## 決定

### 論点 1: 新規生成の既定

1. **`/init-project` は既定で `AGENTS.md` のみを生成し、`CLAUDE.md` は生成しない**
   - 理由: 実体が 1 本になる(design の「実体を 1 つに保つ」)。CLAUDE.md が存在するだけで直読みが止まるため、「AGENTS.md に揃える」には生成をやめる必要がある。§7-4 の「CLAUDE.md への追記は Cursor CLI にも読まれる」注意が完成形では不要になる
   - 却下: 「現状維持(import 1 行を常に生成)」(2 本のまま。橋渡し用の規約が残り続ける)/ 「毎回対話で選ばせる」(質問が増える。利用者が直読み可否を知らないことが多い)
   - 反映先: design §7-4 / init-project(description・原則・Phase 3-1・`CLAUDE.md.template`)/ README

### 論点 2: ホスト固有の追記の置き場

2. **Claude Code 固有の指示は `.claude/rules/*.md` に置く。`CLAUDE.md` は作らない**
   - 理由: `.claude/rules/` は CLAUDE.md の有無の判定に数えられず、直読みと併せて読まれる(公式記載)。Claude Code だけが読む場所なので AGENTS.md の「他ホストでも通じる記述だけ」の原則を保てる。正常形が「CLAUDE.md 無し」の 1 つに揃う
   - 却下: 「AGENTS.md 内にホスト固有の節」(全ホストに読まれる。既決の原則を崩し 32 KiB 上限を圧迫)/ 「必要時のみ `@AGENTS.md`+追記の CLAUDE.md」(正常形が 2 つになる。import を忘れると AGENTS.md が読まれない)/ 「規定しない」(import 忘れの事故を防げない)
   - 条件: **rules と直読みの併存を実機で確認することを、実装時の完了条件に入れる**(確認の場は決定 7)
   - 反映先: design §7-4 / `AGENTS.md.template` 冒頭の案内文 / init-project Phase 3-1

### 論点 3: 導入済みプロジェクトの CLAUDE.md

3. **`/init-project` だけが、承認制で完成形への移行を提案する。他の skill は import を持つ CLAUDE.md を正常な互換形として扱い、警告しない**
   - 移行の内容: import のみの CLAUDE.md は削除 / import+追記の CLAUDE.md は、追記を `.claude/rules/` へ移してから削除
   - 規律: 2026-09-09 決定 6 と同型 — ユーザーの明示承認・他ツール/CI からの `CLAUDE.md` 参照の提示・`--yes` でも省略しない(承認制と参照確認の出所は 2026-09-09 決定 6、`--yes` でも省略しないのは design §7-6 の派生規則と `init-project/SKILL.md` の現行手順)。削除の前に「直読みできない環境で使う人がいないか」の確認を挟む(いれば残す)
   - 理由: 一本道で完成形へ寄せられる。削除は「既存を壊さない」原則の例外なので承認制にする。import があれば二重読みも欠落も起きず、警告する実害が無い
   - 却下: 「放置」(旧形から完成形への導線が無い)/ 「全 skill でドリフト注記」(実害の無い構成への毎回の警告はノイズ。意図的に残した人にも出る)
   - 反映先: init-project(Phase 1-5 の 4 分類・Phase 3-1 の表と移行フロー・最終ゲート)/ design §7-4

### 論点 4: 検出順・ドリフト判定

4. **ドリフト判定は「ルートの 3 種」を見る**: `AGENTS.md` があり、ルートに `CLAUDE.md` / `.claude/CLAUDE.md` / `CLAUDE.local.md` が 1 つ以上あるのに、**そのいずれにも** `@AGENTS.md` の import が無ければ注記し、対処(import の追加、またはユーザー設定を `claude-md-and-agents-md` に変更)を案内する
   - **条件の確定(2026-09-22・反映前レビューを受けたユーザー判断 Q2)**: 壁打ち時の文言は「import を持たない 3 種のいずれかがあれば注記」だったが、互換形に個人用の `CLAUDE.local.md`(import なし)を足した構成は import 経由で AGENTS.md が読まれ実害が無い。決定 3(互換形は警告しない)とも衝突するため、「いずれにも import が無い場合」に確定した。却下: 「文言どおり(1 つでも import 無しがあれば注記)」
   - 理由: `CLAUDE.local.md` は gitignore される個人メモで、置いた人の環境だけ AGENTS.md が読まれなくなる。存在確認が増えるだけで実害の大きい罠を拾える。根拠の事実は design §7-3 に置き、skill 本文には判定手順だけを書く
   - 却下: 「現状のまま(ルートの CLAUDE.md だけ)」(`CLAUDE.local.md` の罠を見逃す)/ 「親ディレクトリも走査」(リポジトリ外を読むことになり understand-project の範囲を超える)
   - import の判定基準は現行を引き継ぐ(コードブロック内・インラインコード内の `@AGENTS.md` は import とみなさない)
   - **判定の精密化(2026-09-22・反映前レビュー)**: 文字列 `@AGENTS.md` の有無ではなく「ルートの `AGENTS.md` を指す import があるか」で判定する(`.claude/CLAUDE.md` では相対パスの基準が変わるため。根拠と未実測の範囲は「実装時の確認事項」の相対パスの行)。上の太字はユーザー回答の文言のまま残している
   - 反映先: design §3(動的検出の標準ロジック)/ understand-project 0-2・Phase 4 / update-doc のドリフト判定 / init-project Phase 1-5

5. **`.claude/rules/` は skills の読取り・同期の対象外とする(ホストの管轄)**。互換形の CLAUDE.md にある追記を補完として読む現行規定は残す
   - 理由: rules はホストが自動で読む。skill 本文のホスト結合を増やさない
   - 却下: 「補完として読み update-doc の検査対象にする」(他ホストで実行したときも Claude Code 専用ファイルを読む。本文のホスト固有パスが増える)
   - 承知した欠点: rules 内に書いたコマンドが陳腐化しても update-doc では拾えない

### 論点 5: 直読み不可環境のフォールバック

6. **案内のみとし、検出はしない**。`/init-project` の完了報告と `AGENTS.md.template` 冒頭に、直読みの確認方法(既定値のもとで出る `AGENTS.md loaded` の行。直読みできないセッションは `/config` に Project instructions が出ないことで判別)と互換形(`@AGENTS.md` を import する CLAUDE.md)の作り方を書く(確認方法の括弧内は、事実欄の訂正に合わせて 2026-09-22 に更新した。壁打ち時は「`AGENTS.md loaded` の行」のみ)
   - 理由: 互換形という逃げ道は決定 3 で確保済み。dev-workflow のフローでは understand-project が権威参照ファイルを必ず Read するため、欠落するのは skills を通さない素のセッションに限られる
   - 却下: 「init-project が 1 問聞いて生成」(質問が増える。利用者が条件を知らないことが多い)/ 「自動検出して生成」(ホスト固有の検出ロジックが skill 本文に入る。実行者の環境しか分からない)/ 「対応しない」(導線が無い)
   - 反映先: init-project Phase 4(完了報告)/ `AGENTS.md.template` / design §7-3(事実)・§7-4(運用)

### 論点 6: このリポジトリ自身の CLAUDE.md

7. **このリポジトリを完成形へ移行する**: Claude Code 固有の 2 項目を `.claude/rules/` 配下へ移し、`CLAUDE.md` を削除する。`AGENTS.md` の「コマンドはホスト固有のため、各ホストの権威参照ファイル側に追記する」の文言を決定 2 に合わせて直す
   - 理由: 配布する規約と自リポジトリの形を一致させる。決定 2 の実機確認(rules と直読みの併存)の場になる
   - 却下: 「互換形のまま維持」(配布規約と食い違う。実機確認の場が別に要る)
   - 移行のタイミング(skills の変更と同じ PR か先行か)は実装タスク側で決める

### 論点 7: `source_of_truth: claude-md` の改名

8. **値名を `agents-md` へ改名し、旧値 `claude-md` は廃止する(受理しない)**
   - 理由: CLAUDE.md が標準構成から消えると「CLAUDE.md が正本」と誤読される。`serena | docs | agents-md` で「置き場の具体名」として並びが揃う
   - 却下: 「旧値も同義として受理」(「旧値も同義」の 1 文が本文に残り続ける)/ 「中立名(`authority-file` 等)」(他の 2 値と並びが揃わない。定着した英語名が無い)/ 「据え置き」(誤読の余地が広がる)
   - 経緯: 回答時にいったん「別エージェントが対応中のため保留」とされたが、直後に勘違いとして取り消され、廃止で確定した
   - 反映先: design §4 / `project-profile.yml.template` / init-project / update-doc / understand-project

9. **`source_of_truth` が有効な 3 値(`serena` / `docs` / `agents-md`)以外なら、skill は停止して有効値を案内する**。旧値は名指ししない(未知値一般の規則として書く)。移行の注記は README と変更履歴に 1 行書く
   - 理由: 絶対規約の型(フォールバック+無視した旨を報告)をそのまま当てると、旧値が既定(serena)に落ち、**update-doc の書き込み先が止まらずに変わる**(報告は出るが書き込みは実行される。壁打ち中は「無警告で変わる」と説明したが、報告は出るので言い過ぎだった)。停止なら誤った書き込みが起きず、利用者は 1 語の置換で解消できる。旧値を名指ししないので本文に `claude-md` が残らない
   - 却下: 「フォールバック+報告」(書き込み先が変わる事故の余地)/ 「書き込み系だけ停止」(規則が 2 系統になる)
   - 「profile が無くても必ず動く」との関係: profile が**無い**場合のフォールバックは変えない。本決定は profile が**あり値が不正**な場合の規則である

### 論点 8: バージョニング

10. **v4.3.0 で出す。design §8 の版の基準は変えない**
    - 理由(選択された案の記述どおり): 影響範囲が小さい(旧値を持つのは、メモリも doc/ も本格運用しない超小規模構成の profile のみ)
    - 却下: 「v5.0.0+§8 に『後方互換を破る変更はメジャー』を追記」/ 「2 段階(v4.3.0 で非破壊部分、値名廃止は次のメジャー)」
    - **承知した緊張**: 決定 8・9 により旧値を持つ profile はマイナー更新で停止する。§8 の「後方互換な機能追加はマイナー」の文言と緊張するが、影響範囲の小ささを理由に承知の上で選択された。決定 9 の移行注記(README・変更履歴)で補う

### 追加論点(2026-09-22・/reflect-decisions の反映前確認 Q1・Q3): 未移行プロジェクトの移行後の形

11. **未移行プロジェクト(`CLAUDE.md` のみ)を `/init-project` が承認制で移行するとき、移行時に選ばせる: 既定は削除(完成形)とし、直読みできない環境・`CLAUDE.md` への外部参照があるときだけ互換形を選べるようにする**
    - 帰結(決定 2 から): 完成形へ移行するとき、Claude Code 固有の記述は `AGENTS.md` ではなく `.claude/rules/` へ移す
    - 互換形を選んだときの Claude Code 固有の記述の置き場は決定 12
    - 理由(選択された案の記述どおり): 決定 3 の「いれば残す」と同じ扱い
    - 却下: 「常に削除して完成形」/ 「常に import 1 行として残す(現行どおり)」
    - 経緯: 壁打ちでは直接扱っておらず、反映案の作成中に判明した。現行の「`CLAUDE.md` を import 1 行に置き換える」の出所は **2026-09-09 決定 5 の後半と `init-project/SKILL.md` の現行手順**であり、2026-09-09 決定 6(承認制の移行提案)は移行後の形を定めていない
    - 承認制と他ツール/CI の参照確認は 2026-09-09 決定 6、`--yes` でも省略しないのは design §7-6 の派生規則(現行の init-project 手順)のまま
    - 反映先: design §7-4 / init-project Phase 3-1 の移行フロー

12. **未移行プロジェクトの移行で互換形を選んだときも、Claude Code 固有の記述は `.claude/rules/` へ移す**(`CLAUDE.md` は `@AGENTS.md` の import 1 行になる)
    - 理由(選択された案の記述どおり): 完成形でも互換形でも固有の記述の置き場が 1 か所に揃う(決定 2 と一貫)。あとで完成形へ移るときは削除するだけで済む
    - 却下: 「import の下に残す(現行どおり)」(固有の記述の置き場が構成によって 2 通りになる)/ 「実装タスクの設計時に決める」

### タスク設計時の追加決定(2026-09-22・/create-task の調査で判明した未定事項)

13. **`.claude/rules/` に置くファイル名は `claude-code.md` で統一する**(このリポジトリ自身も、`/init-project` の移行先も `.claude/rules/claude-code.md`)

    - 却下: 「内容ごとに命名(このリポジトリは plugin-dev.md 等)」/ 「移行時に利用者が指定」(質問が 1 つ増える)

    - 理由(選択された案の記述どおり): 残るファイルは個人ファイルであり、既存を壊さない
    - 補足(タスク設計時): 「個人ファイル」が当たるのは `CLAUDE.local.md`。`.claude/CLAUDE.md` は共有されるファイルだが、skill が作ったものではないので同じく書き込まない

    - 経緯: タスク設計のレビューで判明。symlink は公式が認める構成だが、中身が `AGENTS.md` の本文なので import 行が無く、ドリフトと誤判定される。案内どおりに import を書き足すと、symlink 越しに `AGENTS.md` 自身へ自己 import が書き込まれる
    - 却下: 「今回は扱わない(既知の限界として記録)」
