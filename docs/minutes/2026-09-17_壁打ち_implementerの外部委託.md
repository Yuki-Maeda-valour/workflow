## 決定

1. **implementer の外部委託を開く。オプトイン(宣言)は維持し、宣言された環境では implementer の既定を外部にする。**
   - 理由: §7-2 の「行わない」は明示的な検討の結果ではなく範囲設定だった。毎回の指定を不要にしないと「設計は Claude / 実装は Codex」という運用が成立しない
   - 却下: 「`codex` が PATH にあって認証済みなら宣言なしで外部へ」(コードが宣言なしに外部ベンダーへ渡り課金も自動発生する。design §7-2 の「宣言が無ければ外部 CLI を探しに行かない」と正面衝突)/「開けない(現状維持)」(Codex 併用の利点を捨てる)

2. **起動経路は ③ CLI を自前実装する**(`codex exec --sandbox workspace-write`)。
   - 理由: 柔軟さ = 制御の細かさでは CLI が上。`secret_paths` の除外・ログ規約(何を渡したかの記録)・cwd の限定を自前で持てる。配布物が自己完結する(外部プラグイン・MCP 設定に依存しない)
   - 却下: 「① plugin(`codex:codex-rescue`)に乗る」— **実測で「plugin のほうが柔軟」という前提が成立しなかった**。plugin の機能はすべて codex CLI 由来で、plugin 固有の優位は実装済みのジョブ管理(status / result / cancel)だけ。その代わりに `secret_paths` 除外とログ規約を放棄し、plugin 未導入環境では動かなくなる /「② MCP」— 据え置き(解決表 §5 の「有効化手段が未定・未検証」を動かさない)/「③ を正・① を任意の高速路」— 契約が 2 本になり維持コストが倍
   - 派生: ジョブ管理(進捗・中止)は自前実装が要る
   - 派生(**実測で確定**): **差し戻しは毎回 `codex exec` の新規起動で行い、resume 経路は採らない。** `codex exec resume` が `--sandbox` と `--cd` を受け付けないため、判定 3(フラグの確立)と §9(cwd の限定)をどちらも満たせない — `codex review` を既定表から外した理由(design §7-3)とまったく同じ構造。文脈は渡すプロンプト(前回の diff・レビュー指摘)で補う。これは既存のレビュー経路の扱い(`external-runners.md` §8「外部ランナーは会話継続ができない。再レビューは毎回新規起動」)と一致する

3. **実装は作業ツリーで直接行わせる。** 保護は「**起動前に `git diff` のスナップショットと HEAD を記録** → 実行 → 差分を比較して**外部が書いた分を識別** → diff を提示」。**clean 要求は課さない**(下の訂正②)。
   - 理由: 依存・ビルド環境がそのまま使えるため implementer 自身がテストを回せる
   - **失うもの(訂正あり)**: 失うのは §9-2 限界④の「**取り違えの防止**」と「ユーザーの作業ツリーを汚さない」保証である。**当初「越境読み取りの防止だけ」と書いたのは誤り** — 越境読み取り(限界②「cwd 外の絶対パスを読むことは止められない」)は一時ツリーでも元から防げていない。§9-2 ④ は「一時ツリーは機密の封じ込めではない」と言っているだけで、「取り違えの防止としても不要」とは言っていない
   - 却下: 「git worktree で実装 → diff を適用」(worktree 内に依存〈node_modules 等〉が無いと implementer がテストを回せない)/「実行前に自動 WIP commit」(ユーザーの git 状態を書き換える。§7-2 の原則と衝突)

4. **宣言は profile に許す(既定表の名前のみ)。ただし実行の是非はセッション初回に明示承認を取る。**
   - 理由: 決定 1 の「既定外部」は profile 宣言なしでは成立しない。一方で書き込み委託は「リポジトリを書ける者が、外部に書かせる設定を仕込める」状態を作る。**MCP 宣言(design §7-6)が既に持つ「profile に書いてある = 承認済みとは扱わず、実行前に明示承認を取る」形**を踏襲する
   - 却下: 「profile 可・追加承認なし」(`runners` と同じ扱いにすると書き込み委託で信頼モデルの穴が残る)/「profile 不可・セッション引数のみ」(決定 1 が実質成立しない)

5. **走行中に外部 implementer が落ちたときは、内蔵 implementer が自動で引き継ぐ。**
   - 起動前の失敗(未検出・認証切れ・リミット・読み取り専用〈書き込み範囲〉未確立・無応答)は既存契約どおり **エラーとして報告 + 内蔵編成へ縮退して続行**
   - 走行中の失敗では**残った変更を巻き戻さず**、内蔵 implementer が diff を読んで続きを実装する。**引き継いだ事実と残っていた変更は必ず報告する**(サイレント禁止)
   - 理由: 完走を優先する。巻き戻しはユーザーの git 状態を書き換えるため採らない
   - 却下: 「停止して diff を提示し、続行 / 巻き戻し / 引き継ぎをユーザーが選ぶ」(自動で完走しない)/「巻き戻して内蔵が最初から」(外部が使ったトークンが無駄になり、git 状態も書き換える)
   - 残るリスク: 他者の中途半端なコードを引き継ぐ品質リスク。**決定 7 の diff 突合・チェックリスト照合がスコープ縮小を検出する**ことで担保する

6. **契約は `external-runners.md` を拡張して置く。**
   - 判定順序・終了コード・既定表・ログ規約・機密ガードの手順は**レビューと実装で共有**し、差分(サンドボックスモード・機密ガードの適用範囲・失敗時の扱い)だけ節を分ける
   - 理由: 同じ事実を 2 箇所に書かない(§7-2)。既定表と判定順序の二重管理を作らない
   - 却下: 「新規 `external-implementer.md`」(既定表・判定順序・ログ規約が二重管理になる)/「解決表 + スクリプトだけに持たせる」(散文の義務が守られないことは §7-2 が既に指摘している)
   - 派生: ファイルの副題「(レビュアーのホスト外委託)」は実態に合わせて改める

7. **team-lead 側の検証は現行のまま。** diff 突合・チェックリスト照合・品質ゲート再実行・全 reviewer の APPROVED まで反復を、implementer が誰であっても同じに適用する。
   - 理由: implementer の所在は team-lead の検証構造を変えない
   - 却下: 「外部が書いたときだけゲートを厚くする」(構造が変わらないため不要。決定 3 の diff 提示と決定 7 の突合で足りる)

### その他の見落とし

- **§9-2 限界⑤の悪化**: ランナーはリポジトリ側のルールファイル(`AGENTS.md` 等)を指示として読み、その読み込みは信頼の有無に条件付けられていない。一時ツリーなら影響を捨てられたが、**実ツリー + 書き込み権限では `AGENTS.md` の指示で実ツリーが書き換わる**。維持ではなく悪化なので、新しい限界として書き直す。**このリポジトリに現に壊れた `AGENTS.md`(機械置換で生成されたもの)が未追跡で存在していた**のが実例(#52 で修復)
- **「index / stash / HEAD は動かさない。作業ツリーだけ動かす」を明文化する**必要がある(決定 3 の却下「自動 WIP commit」と決定 5 の却下「巻き戻して最初から」に散っている原則)
- **`implementer: cursor` の互換**: 既定表のランナー名は `cursor-agent` であり `cursor` は既定表外。決定 1 の「既定表の名前のみ」を採ると §1 L24 の規則により **profile から受け付けない(無視して報告)** になる
- **`external-runners.md` L7 の「契約を変えるときはこの 3 点だけ」が 4〜5 点になる**(実装用スクリプトと自己テストが増える)。§11 の「触ったら必ず実行する」の対象も拡張が要る

## 追記④: 2 巡目レビューで判明した欠陥(2026-09-17・同日)

反映版を再度 2 体(外部 CLI + 内蔵上位)にかけた。**両方 `CHANGES_REQUESTED`**。**2 体が独立に指摘した共通項が 3 件**あり、うち 1 件は決定 18 の穴そのものだった。

### 2 体が独立に指摘した共通項

1. **`git status --porcelain` は内容の変化を検出しない** — ファイル名と状態コードしか出さないため、**既存の未追跡ファイルの中身が書き換わっても前後の出力がバイト一致する**(使い捨て git リポジトリで md5 一致を実測)。決定 18 の 3 要素では識別できない

### 最も重い発見: タスク MD がスナップショットの死角に入る

配布スキルの既定のタスク MD(`task/進行中_*.md`)は**未追跡だが gitignore されていない**(`init-project` の gitignore スニペットは `.claude/settings.local.json` / `.claude/reviews/` / `.claude/grasp.md` / `.env` 系 / `export/` のみで `task/` を含まない)。do-task Phase 3 の委託プロンプトは implementer に「タスク MD のチェックボックスを `- [x]` に更新する」ことを**必ず**指示するため、**外部委託の主要な書き込み先の 1 つが上記 1 の死角に入る**。

波及: ①「外部が書いたチェックを信用せず diff から復元する」は**復元元が存在せず成立しない** ②外部がチェックだけ更新して異常終了すると比較結果が「変化なし」→ 縮退に落ち、Phase 4 のチェックリスト突合は**改竄されたチェックを読む**(件数が合うため検出できない)。

### 追加決定

25. **スナップショットを 5 要素にする**(決定 18 を差し替え):
    - ①`git diff --binary HEAD`(追跡分の未コミット差分)
    - ②`git status --porcelain=v1 -z -uall`(全状態の一覧)
    - ③**未追跡かつ非 ignore のファイルのパスと内容ハッシュ**(`git ls-files -o --exclude-standard` の各ファイルを `git hash-object`)。**タスク MD はここで捕捉される**
    - ④`git rev-parse HEAD` + **index の識別情報**(`git write-tree` のハッシュ)
    - ⑤**stash 一覧の識別情報**(`git rev-parse --verify refs/stash`。存在しない場合もその旨を記録して比較可能にする)
    - **比較は ①②③ で作業ツリーを、④⑤ で git メタ状態を見る**
    - **タスク MD は起動前に別途コピーして退避**し、比較・復元に使う(③ があれば検出はできるが、**復元には内容そのものが要る**)

26. **引き継ぎの発火条件に git メタ状態の変化を含める**(決定 20 を拡張): 「**終了コードが 0 以外、かつ ①②③ の作業ツリー比較または ④⑤ の git メタ比較のいずれかに変化がある → 引き継ぎ**」。
    - 理由: 決定 19 が想定した典型例は「外部が `git commit` すると実行後の差分が縮み『差分なし』になる」ケース。作業ツリーだけを見る条件では、**成果を commit して非ゼロ終了した場合に「変化なし」→ 縮退となり、成果が残っているのに内蔵が最初からやり直す**誤分類が起きる
    - **HEAD・index・stash の取得と比較は、成功・失敗を問わず実行直後に必ず通る共通工程**として置く(分岐の後に置くと、検出策が守るべきケースそのものをバイパスする)

27. **契約の 3 部構成は「既存の §1〜§11 の番号を維持し、実装固有を §12 以降に新設する」形で実現する**(決定 17 を修正)。
    - 背景: **外部から `external-runners.md` の節番号を指す参照が 28 行・7 ファイル**ある(`§8` だけで 11 箇所。`delegation-map.md` / `review-protocol.md` / `do-task/SKILL.md` / `init-project/SKILL.md` / `design.md` / `review-agent.sh` / `review-agent-selftest.sh`)。完全な再編では 28 行すべてを追随させる必要があり、**`validate.py` のリンク検査はアンカーを除外し `docs/` と `README.md` を走査しない**ため機械検査が一切効かない
    - 既存節は番号も内容も動かさず、**各節の冒頭に「この節はレビュー経路の契約。実装経路は §12 以降」の 1 行を添える**。共通で使える節にはその旨を書く
    - 却下: 「完全に 3 部へ再編」(参照 28 行の追随が無主になり、見落としを機械検査で拾えない)/「節に安定アンカーを与えてアンカー参照に変える」(根本解決だが全参照スタイルの変更で今回のスコープを大きく超える)

## 追記⑦: 5 巡目レビューの結果(2026-09-17・同日)

3 体にかけた。前回 15 件のうち **11 件は完全反映**。残りは #57(配線側)への伝播漏れ。加えて**決定 32 の根拠が実測で偽であること**が判明した。

### 実測で判明した欠陥: 「リポジトリ外」は外部プロセスから守れない

| 置き場 | 書き込みモードの外部プロセスから | 判定 |
|---|---|---|
| `/tmp/tmp.XXXX`(`mktemp -d` の既定) | **上書き成功**(rc=0、内容が TAMPERED に) | ✗ 守れない |
| `$HOME/.cache/...`(repo 外 **かつ** tmp 外) | `Read-only file system`(rc=2、内容は ORIGINAL のまま) | ✓ 守られる |
| `/tmp` + `exclude_slash_tmp=true` | `Read-only file system`(rc=2) | ✓ 守られる |

既定の `workspace-write` サンドボックスは **`/tmp` と `$TMPDIR` を書き込み可能にしている** — `sandbox_workspace_write` に `exclude_slash_tmp` / `exclude_tmpdir_env_var` という**除外オプションが存在すること自体がその証拠**(この事実は追記③の時点で記録済みだった)。

したがって決定 32 の移設で塞がったのは理由②(比較の視野に入らない)だけで、**理由①(外部が書けない)は成立していない**。「改竄されたコピーから復元してしまう」経路は残っていた。

**さらに**: 退避コピーは外へ出したのに、**比較の基準であるスナップショット本体は `.claude/reviews/`(ツリー内)に残したまま**で、決定 31・32 により ①②③ の全比較から除外されていた。つまり「外部が書ける **かつ** 改竄が検出されない」という**同じ条件を満たすものが半分残っていた**。基準が差し替われば ①②③ の比較結果自体が偽になる。

### 追加決定

    - **(a) 要件語の変更**: 退避コピーとスナップショット本体は**外部の書き込み範囲外**に置く。「リポジトリ外」では不十分(実測)。具体的な場所(`$XDG_STATE_HOME` / `~/.cache` 相当)は契約側に書き、**ホスト非依存の要件語は「外部の書き込み範囲外」**とする
    - **(b) ハッシュ突合(必須)**: **復元前に、退避コピーのハッシュを ③ で記録した起動前ハッシュと突合し、不一致なら復元を中止して報告する**。③ は同じファイル集合のハッシュを既に持っているので追加コストはほぼゼロで、**置き場所の保証に依存せず改竄を検出できる**。(a) が破られても (b) が残る二重防御にする
    - **(c) スナップショット本体も同じ扱い**: 比較の基準が改竄されると ①②③ の結果自体が偽になるため、退避コピーと同じ場所へ移す
    - **(d) 除外の縮小**: (c) の結果、決定 31 の「①②③ から除外」の対象は**ログだけ**に縮む。これにより「`.claude/reviews/` が追跡されているプロジェクトでは、外部が同ディレクトリ内の追跡ファイルを書き換えても ① が拾わない」という**除外を広げたことの副作用**も消える
    - **(e) 退避と復元の保存形式**: **リンクとモードを保存する形で行う**(`cp -a` 相当)。素の `cp` は symlink を実体化しモードを落とすため、**復元処理そのものが改変になる**(実測)。退避の取得に失敗したエントリは ③ と同じく**当該エントリのみ記録して続行**する(ディレクトリへの symlink は `ls-files -o` に列挙されるが `hash-object` が exit 128。実測)
