## 既決との関係

- **ship-task の関連スキル節「タスク MD が既にある場合: このスキルではなく /do-task から始める」を変更する**(決定 1)。既存のタスク MD から ship-task を始める入口ができるため
- design §5-10(コストで打ち切らない・報告点)は**変えない**。無人では「判断を仰ぐ」手段が `保留_` になるだけで、基準は下げない(決定 5)
- design §5-5 は**変えない**。人のシェル・cron から起動するループは規約の対象外であることを明記する(決定 12)
- 外部 implementer の承認契約(セッション初回の明示承認)は**変えない**(決定 8)
- design §4 の信頼モデルは**変えない**。起動コマンドの上書きと許可リストを profile に置かない(決定 7・11。壁打ちの途中で、当初の決定 11「profile で上書き」がこれと矛盾することに気づき、修正した)
- design §5-1 の状態名に `候補_` を加える(決定 14)。**#48 の「状態名・ブランチ名の規約は変更しない」を変える**(ユーザーは状態名に加える案を明示して選んだ)。正本 `task-directory.md`・helper の変更は #69 で行う。#48 の検出規則への影響(`候補_` だけのディレクトリが task_dir の候補になる)は #69 に申し送る
- **ship-task の「停止時はタスク MD を stage しない」を、無人モードでは読み替える**(決定 3。`保留_` への改名と理由を作業ブランチに commit する)
- design §7-2・§7-6 の前提「既存の設定はホストのゲートが守る」は、ヘッドレスではゲートが働かないため無人ループには当てはまらない(決定 16)
- do-task 原則 4・Phase 6(`--max-iter` は報告点)は変えない。無人モードの読み替えは決定 5 と同じ
- 「無人では、気づかないまま別の場所に書くより、止まって報告するほうが安全」は #94 の決定(置換漏れは停止)と同じ方向である
- 親 #65 のスコープ外(並列ループ・機能追加の自動起票・PR の自動 merge)は維持する

## 決定

### 論点 ①: 位置づけと名前

1. **skill は増やさない。ship-task に「既存のタスク MD から始める入口」と「無人モード」を足し、外側の while は同梱のスクリプト `loop.sh` が回す。git の出口は ship-task のまま**
   - 1 周 = ホスト CLI をヘッドレスで起動し、`/ship-task <タスク MD>` を無人モードで走らせる(Phase 1 を飛ばし、Phase 2 の続行判定から do-task → update-doc → PR)
   - **接続条件(決定 1・6 と §5-20 から導く。#67 で実装)**: 周はデフォルトブランチ(決定 19)から作ったブランチの無い worktree(detached HEAD)で始まる。既存のタスク MD から始める入口では、ship-task が detached HEAD を受け入れ、**Phase 2 より前に**作業ブランチ `task/{名}` を作る(ship-task の Phase 0 の 4 はデフォルトブランチか作業ブランチかしか扱っておらず、ブランチ作成は Phase 1 の後にあるため)
   - `loop.sh` は skill ではない。人のシェル・cron から起動する
   - 理由: while を skill にすると、1 つのセッションの中で回ることになり「1 周 = 新しい文脈」が崩れる。1 周の中身は ship-task の Phase 2〜5 そのもので、git の出口も ship-task だけが持つ(§5-20 を変えずに済む)。skill の数と責務が変わらない
   - 却下: 新 skill `loop-task`(周ごとに skill が 2 段重なり、ship-task と責務が重なる)/ `ship-task --loop`(1 セッションで複数タスクを回すため、文脈の汚染・圧縮で精度が落ちる)
   - 反映先: design §2(位置づけ 1 行)/ ship-task(#67)/ `loop.sh`(#68)

### 論点 ②: キューと状態

2. **ループが拾うのは、タスク MD にメタ行(例 `> **無人実行**: 可`。名前は仮)がある `進行中_` だけ**
   - 理由: 人が手で進めているタスクと衝突しない。宣言しなければ何も変わらない、という既定オフの原則と合う
   - 却下: すべての `進行中_`(人が進めている途中のタスクも拾う)
3. **(改訂)無人の周が止まったタスクは、ship-task の無人モードが既存の `保留_` に改名し、理由(どの停止条件に当たったか・人が次にすること)を追加修正記録に書き、作業ブランチに commit する。`loop.sh` は改名しない(周が落ちたときの扱いは決定 6、時間切れ・許可待ちで固まった周は決定 18)**。完了条件の改竄や ship-task の Phase 0 の 3 の停止など「失敗扱い」の周の落とし先は #67 で決め、決定 6・18 の側に落とすならこの決定の例外として書き足す
   - 理由: `進行中_` のまま残すと次の周で拾い直して無限に再試行する。停止条件を知っているのは ship-task なので、理由を細かく書ける。commit しないと、改名が worktree の未 commit の変更になり、作業ブランチにも残らない
   - 却下: 新しい状態名(例 `要確認_`。状態名と検出の正規表現が増える)/ `loop.sh` だけが書く(終了コードと出力しか見えず、理由の粒度が粗い)
   - **改訂の経緯**: 壁打ちでは「周が落ちて状態が残らなかったときだけ `loop.sh` が `保留_` にする」を含めていた。レビューで、`loop.sh` の改名には置き場が無いと分かった(人のチェックアウトに触れず〈決定 6〉、commit もブランチ作成もしない〈§5-20〉ので、未 commit の変更になるだけ)。ユーザーの判断で、落ちた周は決定 6 の「worktree を残す」で扱う形に改めた
4. **処理順はタスク MD の `> **作成日**` の古い順。同じ日ならファイル名順**
   - 理由: 決定的で、do-task の追記で順番が変わらない
   - 却下: 更新時刻の古い順(追記・チェックアウトで順番が変わる)/ 優先度のメタ行(欄と規則が増える)

### 論点 ③: コスト上限と既定方針

5. **design §5-10 は変えない。無人モードでは、報告点(同一指摘の 2 回連続残存・5 ラウンド超え・`--max-review` / `--max-iter` 到達)に達したら `保留_` にして人に返す。周ごとに壁時計の上限を設ける**(超えた周の扱いは決定 18。壁打ちでは「超えたときも `保留_`(理由: 時間切れ)」と決めたが、2 巡目のレビューで、ship-task が期限を知らないと書く主体がいないと分かった)
   - 理由: 品質基準を下げない(未収束のまま PR を出さない。無人で続行もしない)。1 タスクが夜全体を使い切らない。時間の上限はどのホストでもかけられる(トークン・金額の上限はホスト CLI の機能に依存する)
   - 却下: 報告点でも無人で続行し、時間の上限だけで止める(同じ指摘の空回りで予算を使い切りやすく、§5-10 の「人の判断」を飛ばす)/ N 巡で打ち切って未収束の PR を出す(ship-task 原則 4 と §5-10 を書き換えて基準を下げる)
   - 反映先: design §5-10(無人時の読み替え 1 行)/ §4 `features.loop`(周の時間上限)

### 論点 ④: 隔離と権限

6. **(改訂)周ごとにデフォルトブランチ(どの ref かは決定 19)から使い捨ての worktree を作り、その中で 1 周を走らせる。人のチェックアウトには触れない。周が正常に終わった(ship-task が PR を開いたか、`保留_` を commit した)ときだけ worktree を消す。落ちた・時間切れ・未 commit が残った周は worktree を消さずに残し、そのタスクは以後拾わない(残った worktree が除外の印。決定 9)。ループは次のタスクへ進み、連続する失敗はブレーカー(#68)で止める。残った worktree は朝の報告に並べる**
   - 理由: 落ちた周の作業を消さない(「clean して main へ戻す」は破壊的)。人の作業ツリーと衝突しない。1 タスクの失敗で夜の残りを止めない(決定 5 の「1 タスクが夜全体を使い切らない」を保つ)。ブランチを作る前に落ちた周でも、残った worktree で二重に拾わない
   - 却下: 同じチェックアウトで周の終わりに main へ戻す(専用の clone が前提になる)/ 未 commit を clean して続行(落ちた周の作業が消える)/ `loop.sh` にブランチ作成と commit を許す(§5-20 に例外が要る)/ 異常な周でループ全体を止める(壁打ちでの当初の形。時間切れ・落ちた周で夜の残りが止まる)
7. **(改訂)権限は許可リストで最小化して走らせる。全許可のモードは無人ループでは使わない。許可の要る操作が拒否された周は `保留_` にする(待ちのまま固まった周の扱いは決定 18)。許可リストは利用者の側(ホストの利用者設定・`loop.sh` の起動引数)にだけ置き、profile などリポジトリが書ける場所には置かない**
   - 理由(置き場): リポジトリを書ける者が無人実行の権限を広げられないようにする(design §4 の信頼モデル)。具体的な渡し方はホストごとの起動事実として #68 で実測する
   - 理由(全許可を使わない): Claude Code の全許可フラグは「インターネット接続の無いサンドボックスでだけ推奨」で、ネットワークが要るループとは両立しない
   - 却下: コンテナ必須(導入の手間が大きい)/ 利用者任せ(危険を明記するだけ)/ 許可リストを profile に置く(リポジトリを書ける者が権限を広げられる)/ 全許可をコンテナ等の隔離環境でだけ許す(壁打ちでの当初の形。ホストの推奨〈ネットに繋がない〉から外れる)/ ネットワークを絞った隔離環境でだけ全許可を許す(導入の手間が大きい)
8. **無人モードでは外部 implementer を使わない(内蔵 implementer で走る)**
   - 理由: 外部 implementer の承認は「セッション初回の明示承認」という契約で、無人では得られない。契約を変えずに済む。ship-task の「承認が無ければ内蔵で走り切る」と同じ挙動になる
   - 却下: `loop.sh` 起動時の 1 回の承認を全周に効かせる(セッションを跨いで承認を持ち越す契約への変更と、承認の証拠の置き場の設計が要る)/ profile の宣言で承認とみなす(「引数・設定では省略できない」を覆す)
9. **(改訂)同じタスクを二度拾わない判定は git の状態で行う。作業ブランチ `task/{名}` がローカルかリモートに在るタスクと、決定 6 で残った worktree があるタスクは拾わない(PR 待ち・保留中・落ちた周を含む)。専用の状態ファイルは持たない。各周の結果(PR / 保留の理由)は `loop.sh` の朝の報告で一覧にする**
   - 背景: 決定 6 の worktree 方式では、`保留_` / `完了_` への改名はその周のブランチにだけ入り、キューを読むデフォルトブランチ(決定 19)には、PR が merge され、人がローカルを更新するまで現れない(壁打ち中に見つけた矛盾)
   - 却下: ループ専用の台帳(リポジトリ外。消えると二重に拾う)/ main の task_dir へ状態を書き戻す(決定 6 の「人のチェックアウトに触れない」と衝突)
10. **無人実行は、タスク MD が worktree の元になるデフォルトブランチ(決定 19)に commit 済み(task_dir が git の追跡下)であることを前提にする。追跡外なら `loop.sh` は起動時に理由を出して止まる**
    - 理由: デフォルトブランチ(決定 19)から作った worktree に、追跡外のタスク MD は存在しない
    - 却下: `loop.sh` が worktree へ写す(写した先の `完了_` / `保留_` がどこにも残らない)
(決定 16・17 はレビュー後に足した。論点 ④ に属するので、ここに置く)

16. **(追加)無人の周では、リポジトリ側のホスト設定(プロジェクトの許可規則・hook・MCP 宣言など)を読み込ませない起動を、`loop.sh` の既定表の既定にする。読ませない手段はホストごとに #68 で実測して §7-3 に記録する。手段が無いホストでは無人ループを起動しない**
    - 理由: ヘッドレス起動ではホストの承認ゲートが働かず、リポジトリを書ける者が無人実行の権限を広げられる(決定 7 の理由と同じ。profile に置かないだけでは足りない)。必要な許可は利用者の側で渡す(決定 7)
    - 却下: 起動時に人がリポジトリ側の設定を確認する(cron での無人起動と両立しない)/ 受け入れる限界として明記する
    - 候補の手段(`--help` で実在を確認。効き方は未実測): Claude Code の `--setting-sources` / `--strict-mcp-config`、Codex の `--ignore-rules`、Cursor CLI では `--approve-mcps` を付けない
    - 候補の副作用(レビューで指摘。#68 で確かめる): Claude Code の `--safe-mode` は skill・導入済みプラグイン・CLAUDE.md も読まないので、周の中の /ship-task が動かず**候補にならない**。`--setting-sources` から `project` を外すと、プロジェクトの設定で有効にしたプラグインまで外れうる。Codex の `--ignore-rules` は利用者の `.rules` も読まないので、決定 7 の「許可リストは利用者設定」とぶつかる(`-c` などの起動引数で渡せるかは #68 で実測)。Claude Code の `--restricted` は利用者・プロジェクト・ローカルの設定ファイルを読まず(managed settings と `--settings` は効く)、全許可のモードを拒否するが、`--tools` で名前を挙げない限り Bash などコードを実行するツールと WebFetch を外す。MCP サーバーは `--strict-mcp-config` を併せないと読まれ、settings・git・ツール設定ファイルへの書き込みは人か設定済みの承認ハンドラだけが承認できる(比較の候補)
17. **(追加)#90 の K1(再開判定)・K5(設計レビューの APPROVED をタスク MD に残す)を、#90 から #67 の前提へ移す**(移した先は決定 20 で #103)
    - 理由: 使い捨ての worktree には gitignore 対象の設計レビュー記録が無く、ship-task の Phase 2(設計レビューの APPROVED の確認)で毎周止まる
    - 却下: #67 の中で扱う(#67 が大きくなる)
- (前提・既決)merge はしない(ship-task 原則 5・最終ゲート)

### 論点 ⑤: 起動事実の置き場

11. **ヘッドレス起動の事実(起動コマンド・非対話のフラグ・許可リストの渡し方)は、出典つきで design §7-3 に置く。実際に使うコマンドの雛形は `loop.sh` の既定表(ホスト名 → 雛形)に置く。上書きは `loop.sh` の起動引数だけで受け付け、profile に書かれていても無視して報告する。skill 本文と解決表には書かない。役割語は増やさない(起動は委託ではない)**
    - 理由: 外部ランナーの既定表と同じ流儀になる。起動引数は、ループを起動する人がシェルで与えるもので、セッション内の発話と同じ扱いにできる(design §4 の信頼モデルを崩さない)。解決表は CLI 名を持たない前提(`validate.py`)を崩さない
    - 却下: 解決表に「起動」の軸を足す(CLI 名を持たない前提を崩す)/ `external-runners.md` の既定表に足す(委託〈レビュー・実装〉の契約と起動の契約が混ざる)/ profile での上書き(当初はこの形で合意したが、信頼モデルとの矛盾に気づいて改めた。MCP 宣言のような実行前の承認は無人では取れない)
12. **design §5-5 は、ホストのセッションの中からホストと同じ CLI を起動することを禁じる規約であり、人のシェル・cron から起動する `loop.sh` は対象外だと明記する。`loop.sh` は起動時にホストのセッションの中でないかを判定し(`external-runners.md` §3 判定 2 を流用。判定 2 と同じくベストエフォートで、判定できないホストは素通りする)、中と判定したら止まる**
    - 理由: ホストのセッションの中から Bash で `loop.sh` を叩くと、入れ子起動・二重課金になり §5-5 に違反する
    - 却下: 対象外と明記するだけ(機械的に拒否しない)

### 論点 ⑥: 発見ループの線引き

13. **人の採用を飛ばして `進行中_` に積む領域は設けない。発見ループは `候補_`(指摘・根拠・発見元)を積むだけで、採用は人が /create-task に通す。例外は運用の実績を見てから別に決める**
    - 理由: 「何を作るか」を機械に渡さない(親 #65 のスコープ外と同じ線)。/create-task は対話と設計レビューを含む
    - 却下: 限定領域(CVE 起因の依存更新・lint・型の既知パターン・doc ドリフト)だけ飛ばす(発見ループが無人で create-task を通し、決定 2 のメタ行まで付けることになる)/ 発見ループを当面作らない
14. **`候補_` は状態名として task_dir に置く(design §5-1 の状態名と、検出の正規表現に加える)。書式の詳細は #69 で決める**
    - 理由: 人が見る場所が 1 か所で済む
    - 却下: 別の置き場(例 `task_dir/candidates/`。検出・helper は変わらないが、見る場所が 2 か所になる)

### 論点 ⑦: #81 は #68 の前提か

15. **#81(外部 implementer の作業ツリー保護の残り)を #68(`loop.sh` の実装)の前提にする**
    - 理由: 安全側を優先する(ユーザー判断)。決定 8 で無人では外部 implementer を使わないが、それでも #81 を先に片付けてからループを実装する
    - 比較した案: 前提にしない(決定 8 により、ループが #81 の穴を通らないため。推奨として提示した)

18. **(追加)時間切れ・許可待ちで固まった周は、決定 6 に一本化する**: 周の時間上限は `loop.sh` が打ち切るだけにする。時間切れの周と、許可待ちで固まった周は、worktree を残して以後拾わず、理由は朝の報告に出す。`保留_` にするのは、ship-task が自分で止まれたとき(報告点・許可の要る操作の拒否・停止条件)だけ
    - 理由: ship-task が期限を知らなければ、「時間切れ → `保留_`」を書く主体がいない(決定 5 の当初の文言は成り立たない)。仕組みが 1 層で済む
    - 却下: 2 段の上限(ship-task に残り時間を渡し、上限の手前で自分で `保留_` を commit させる。超えて強制終了した周だけ worktree を残す。途中の作業がブランチに残るが、期限の渡し方と打ち切り方を #67・#68 で決める必要がある)
19. **(追加)キューを読み、worktree を作る元の ref は、ローカルのデフォルトブランチ**: fetch はしない(`loop.sh` の git への書き込みは worktree の作成・削除だけ、を保つ)。リモートの作業ブランチの有無は読み取りだけ(ls-remote など)で確かめる。ローカルのデフォルトブランチを最新にするのは人
    - 理由: 決定 6 の改訂で書いた「リモートの最新」は、fetch を許すかが未決で、§5-20 の「git への書き込みは worktree の作成・削除だけ」とぶつかっていた。決定 10 の前提(ローカルでの commit)とも揃う
    - 却下: 起動時に fetch してリモートの最新から読む(タスク MD は push 済みが前提。§5-20 に「取得は行う」を足す)
    - 帰結(3 巡目のレビューで指摘): ① ローカルのデフォルトブランチにある未 push の commit が、無人の周が開く PR に混ざる(ship-task の Phase 0 の 3 が警告するのは未 commit の変更だけ)。② リモートで merge 済みでも、人がローカルを更新するまではそのタスクが `進行中_` に見える。ローカルとリモートの作業ブランチを両方消すと拾い直す。①② の扱い(例: ローカルがリモートより先に進んでいたら起動時に止めるか報告する)は #68 の未決
20. **(追加)K1・K5 は #90 から切り出して新しい Issue(#103)にし、#67 の前提にする**
    - 理由: #90 は K2・K9 の答えを #67 に待つので、#90 ごと #67 の前には置けない(互いを待つ順序になる)
    - 却下: #90 を 2 回に分け、K1・K5 だけ先に直す
