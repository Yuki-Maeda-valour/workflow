## 決定

### 論点 1: 委託の抽象

1. **skill 本文は役割語のみで委託を書く**。ホスト固有の語(`Agent` / `SendMessage` / `Explore` / `general-purpose` / モデルエイリアス)は本文から排し、references の解決表に集約する
   - 理由: §3 が禁じる「事実のハードコード」をツール軸でやっている状態の解消。新ホストが増えても表を 1 行足すだけで済む
   - 却下: 「役割語 + 既定を括弧書き」(本文にホスト名が残り中途半端)/ 「ホスト別分岐を本文に書く」(500 行制限を圧迫し、ドリフトの主因を再生産)

2. **委託先の解決順は「① ホスト内蔵 → ② MCP → ③ CLI」で固定**。profile はバックエンドの有効化のみを宣言し、**既定は ① のみ**(現行と同一挙動)
   - 理由: §5-17 の段階判定と同型で既存の設計哲学に収まる。profile 無しでも動く(§3 の絶対規約)。組み合わせが少なくテストできる
   - 却下: 「profile で順序も指定可能」(組み合わせ爆発で回帰テストが非現実的)/ 「役割ごとに指定」(役割数 × バックエンド数のマトリクスになる)

### 論点 2: MCP の位置づけ

3. **MCP のツール接続は profile で 1 回宣言し、`/init-project` が `.mcp.json`(Claude Code)と `.codex/config.toml`(Codex)を生成する**。MCP サーバー自体は同梱しない
   - 理由: 「同じ MCP をどの AI からも」を実現する最小の形。§3 の 3 層吸収と同型(1 つの事実 → ホスト別に展開)。skills 集という性格を保てる
   - 却下: 「検出と案内のみ(現状)」(AI 非依存化に寄与せず、人間の規律依存になる)/ 「MCP サーバーも同梱」(別プロダクトになり、207 箇所の結合を何も解決しない)

4. **MCP 宣言にも PR #1 で確立した信頼モデルを適用し、起動前の明示承認を必須とする**
   - 理由: `.mcp.json` / `.codex/config.toml` / profile はいずれも commit される共有ファイル。敵対的リポジトリが任意の MCP サーバー(= 任意のコマンド)を宣言できる。PR #1 で同型の任意コード実行を PoC 再現済み
   - 補強: Codex 側も「信頼済みプロジェクトのみ読む」という同じ発想のゲートを持つ

### 論点 3: 権威参照ファイル

5. **`AGENTS.md` を正本とし、`CLAUDE.md` は `@AGENTS.md` の import 1 行にする**
   - 理由: Claude Code は AGENTS.md を読まないため何らかの橋渡しが必須。import は公式サポートされた方法で、実体が 1 つに保たれドリフトが原理的に起きない。中立な名前が正本になり AI 非依存の方向と一致
   - 却下: 「symlink」(Windows チェックアウトと `setup.sh --copy` 系で実体化され意図が崩れる。今回 review-agent.sh の配布で同系の問題を踏んでいる)/ 「CLAUDE.md が正本」(Codex 側の import 構文が未確認で、無ければ複写になる)/ 「両方に同じ内容」(ドリフトの意図的な再生産)

6. **`/init-project` は既存 `CLAUDE.md` を検出したら AGENTS.md への自動移行を提案し、承認を得て実行する**
   - 理由: 差分提案だけでは移行が進まず、Codex を使い始めたときに初めて問題に気づくため
   - **リスク(要対応)**: 他ツールや CI が `CLAUDE.md` を直接参照している場合に壊れる。移行提案時にその確認を挟むこと
   - 却下: 「差分提案のみ・自動変換しない」(既存を壊さない原則には忠実だが移行が進まない)

### 論点 4: 本文の非結合化

7. **基盤(解決表 + 規約)を先に入れ、その後 skill 単位で結合の多い順に移行する**(init-project 39 → do-task 28 → create-task 23 → update-doc 21 → understand-project 21 → 以下順次)
   - 理由: 各回で検証でき、失敗しても影響が 1 skill に限定される。今回の PR が 18 ファイルの変更で 5 反復・66 件の指摘を生んだ実績から、分割の価値は実証済み
   - 却下: 「一括(1 タスク・1 PR)」(レビュー不能な規模)/ 「役割種別で横断」(1 回の変更が全 skill に及び、skill ごとの文脈を見る作業と相性が悪い)
   - (2026-09-09 追記: この順序列は**測定範囲・語彙が明記されていない**。design は範囲・語彙を明示した実測〈SKILL.md のみ・9 トークン〉を持ち先頭が入れ替わるため、design には固定列を書かず「結合の多い順・着手時に測り直す」という原則のみを採る。**決定の趣旨(結合の多い順)は維持**)

8. **退行防止は機械検査とレビュー観点の両方**。`validate.py` に「移行済み skill の本文にホスト固有語が無いこと」の検査を追加し、レビュー観点にも「ホスト結合の混入」を加える
   - 理由: 207 という数字が測定可能な不変条件になる。段階移行と相性がよい(移行済みの skill だけ対象にできる)。今回 validate.py のリンク検査拡張で同手法が効くことを実測済み
   - 機械検査だけにしない理由: 今回 selftest の空アサーションが 44 件 PASS を素通りしたように、語彙一致では拾えない文脈依存の結合が残る

### 論点 5: バージョニングと移行

9. **基盤を v3.9.0、skill 移行を 3.9.x で進め、207 箇所の完了時点で v4.0.0**
   - 理由: 「AI 非依存の到達点」をメジャーで示せる。途中の利用者は 3.9.x を使い続けても壊れない。AGENTS.md 移行は承認制なので 3.9.0 に入れても破壊的ではない
   - 却下: 「全てマイナー」(完了の節目がなく移行がだらだら続く)/ 「v4.0.0-rc から」(rc が長期化すると本番利用をためらわれる。このリポジトリに rc 運用の前例がない)

10. **PR #1(v3.8.0)を先にマージし、基盤で CLI バックエンドを ③ に位置づけ直す**
    - 理由: 3 レビュアー APPROVED で品質は担保済み。MCP サーバーが無いベンダー(gemini 等)では ③ が唯一の経路なので実装は無駄にならない
    - 却下: 「基盤の設計を PR #1 に追加してから」(PR が再び大きくなり APPROVED を取り直す必要がある)/ 「PR #1 を閉じてやり直す」(5 反復・66 件を消化した成果を捨てることになる)

## 認証後の実測で判明した事実と決定(2026-09-09)

両 CLI の認証が通ったため、実物で検証した。

### 実測で確認できたこと

- **`cursor-agent` はワークスペースの信頼を要求する**。既定表のコマンド(`--mode ask --model {model} -p --output-format json`)では `Workspace Trust Required` で終了コード 1 になり、非対話実行できない。`--trust` を足すと通る(`--trust` はワークスペース信頼のみで、コマンド許可の `-f` / `--yolo` とは別物。読み取り専用は `--mode ask` が担保したまま)
- **実 CLI が実際にレビューを返すことを初めて確認**。`cursor-agent --mode ask --trust --model gpt-5.2 -p --output-format json` が bash 関数のレビューを返した
- **出力は二重エンコードの封筒**(`{"type":"result","result":"<JSON 文字列>"}`)。`review-agent.sh` の正規化器はこれを正しく処理できることをスタブで確認済み(exit 0・既存スキーマへ変換)
- **`codex review` は `--uncommitted` とカスタムプロンプトを併用できない**。また `--cd` / `--sandbox` を受け付けない(オプションは `-c` / `--strict-config` / `--enable` / `--uncommitted` / `--base` / `--disable` / `--commit` / `--title` のみ)
- **外部 CLI はリポジトリ境界を越えて読む**。`codex review` にカスタムプロンプトを渡した実行で、**カレントリポジトリ外の兄弟ディレクトリにある別プロジェクトのファイルパスが出力に現れた**(既定サンドボックスは restricted fs だが読み取りは越境する)。§9 に「一時ツリーを使えても cwd 外の絶対パス読み取りは防げない」と限界として書いていた事象が、実際に起きることを確認した

### 決定(改訂・追加)

14. **CLI バックエンド ③ の Codex は `codex exec -C <一時ツリー> -s read-only` を既定とする**(決定 12 を撤回)
    - 理由: 決定 12 は「`--uncommitted` が未追跡ファイルを含むので一時ツリーが不要になる」ことを根拠に採択したが、**一時ツリーの本来の目的は機密の遮断**であり、`codex review` はそれを適用する手段(`--cd`)を持たない。利便性と引き換えに機密ガードを失う取引になっていた
    - `codex exec` は `-C <DIR>`(作業ルート)と `-s read-only`(サンドボックス)を持ち、レビュー観点と JSON 形式もプロンプトで指定できる
    - 影響: PR #1 の既定表(`codex exec`)は変更不要。未追跡ファイルは既存の一時ツリー手順で運ぶ
    - 却下: 「`codex review` を使い機密ガードを諦める」(実測で越境が確認された以上、採れない)/ 「両方を既定表に持つ」(1 ランナー 2 エントリになり肥大化を招く。選択の判断を利用者に押し付ける)

15. **一時ツリー方式を「推奨経路」から「必須」へ格上げする**。外部 CLI を使うときは一時ツリーを作り、**cwd を限定できないランナーは既定で無効**にする
    - 理由: 越境読み取りが実測で確認された以上、推奨に留める根拠がない。クライアント案件を含む他プロジェクトのパスが外部ベンダーに渡る事態は防がねばならない
    - 影響: 一時ツリーを作れない構成(非 git プロジェクト)では外部 CLI が使えなくなる。これは意図した縮退とし、理由を報告する
    - 却下: 「限界として明記するに留める」(実害が確認されたリスクを利用者の注意力に任せることになる)

16. **既定表の `cursor-agent` 行に `--trust` を追加する**(実装上の欠陥修正)
    - 理由: 現状の既定表では Cursor をランナーとして起動できない。v3.8.0 に含まれる実害のある不具合
    - 検証: selftest に「Workspace Trust が要る環境で `--trust` 無しなら probe-failed」を再現するケースを足す
