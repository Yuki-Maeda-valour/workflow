# タスク MD 標準フォーマット

解決したタスクディレクトリの `進行中_{タスク名}.md` はこの構成で生成する。「(任意)」の節は該当するときだけ含める。
このフォーマットは /do-task が機械突合(チェックボックス集計・スコープ縮小検出)に使うため、章立てとチェックボックス記法を崩さないこと。

```markdown
# {タスク名}

> **ステータス**: 🚧 進行中
> **作成日**: {YYYY-MM-DD}
> **関連**: {PR / Issue / 会話の参照(あれば)}
> **品質維持契約**: {`--compact` から通常形式へ戻った場合のみ、checker・設計レビュー・実装と検証の分離・実装後独立レビュー・品質ゲート・実動確認を省略しない旨を記載。それ以外は行ごと省略}
> **無人実行**: {可 — 無人ループに拾わせるときだけ人が付ける。それ以外は行ごと省略}
> **発見元**: {候補から採用したときだけ。候補の行を引き継ぐ(記法の規約の「採用の引き継ぎ」)。それ以外は行ごと省略}
> **指摘キー**: {同上}

## 概要

{何を・なぜ。2〜5 行。ユーザー要求の原文の要点も残す}
```

## 記法の規約

- チェックボックスは `- [ ]` / `- [x]` のみ(全角・別記号を使わない)。/do-task が `grep -cE '^\s*- \[(x|X)\]'` で集計する
- 品質ゲートコマンドはプレースホルダのまま残さず、profile / scripts 検出で解決した実行形(例: `pnpm check`)を書く
- 「段階的に実施」「後続タスク」「今回はスコープ外」等の表現を実装タスク内に書かない。スコープ外にするものは必ず「スコープ外」節に契約整合とセットで書く
- **追加修正記録の節**: `## 追加修正記録` の見出しの次の行から、次の `## ` 見出しの前まで(無ければ末尾まで)。見出しの判定では、コードフェンス(下の「本文ダイジェスト」の定義)の中の行を数えない(節の中に貼った `git status -sb` の出力などの `## ` の行で、節が途中で切れないようにする)。下の「設計レビューの行」「保留の行」「記録あり」と、それを使う判定(ship-task の Phase 2・do-task の再開判定・base-commit.md の新規着手の条件 ②)は、どれもこの範囲だけを見る
- **設計レビューの行**(create-task が書く。改行を含まない 1 行。節の末尾に足す): `- **設計レビュー**(create-task・YYYY-MM-DD): <判定> — checker: <指摘 0 | 指摘 N 件残存> / 反復 <N> 回 / 編成: <役割名の列挙> / 本文: <本文ダイジェスト | 算出不能> / needs-user: <なし | 項目>`(括弧は ASCII。checker の件数は valid 指摘の数)。追加修正記録に create-task が書くのはこの行だけ(調査のメモなどは本文か `.claude/reviews/` へ)
  - 判定の語は 3 つ: `APPROVED`(checker の valid 指摘 0〈invalid は理由を記録して却下済み〉**かつ**全レビュアーの valid 指摘 0)/ `未収束`(反復しても指摘が残った。報告点でユーザーが打ち切りを選んだ場合も含む)/ `未完了`(レビュアーを起動できない・途中で止まった・やり直しの途中)
  - 照合パターン(方言は `grep -E` = POSIX 拡張正規表現): `^- \*\*設計レビュー\*\*\(create-task・[0-9]{4}-[0-9]{2}-[0-9]{2}\): (APPROVED|未収束|未完了) — `。ship-task の Phase 2 は、節の中でこれに一致する**最後の行**で判定する
  - `本文`: 行を書く時点のタスク MD の本文ダイジェスト(下の定義)。算出できなければ `算出不能` と書く。位置は `needs-user` の前(needs-user の項目は自由記述なので最後に置く)。値は、前後を固定したパターン(`grep -E`)で取り出す: `/ 本文: (sha256:[0-9a-f]{16}|算出不能) / needs-user: `。v4.5.0 の書式の行には `本文` が無い(照合パターンには一致するので、設計レビューの行として数える)。ship-task の Phase 2 の 6 が、この値と現在の本文ダイジェストを照合する(行と設計の中身を結び付ける)
  - やり直し: 既存のタスク MD を設計し直すときは、節の既存の行を残し、書き換える前に**先に `未完了` の行を足す**(途中で止まっても、古い `APPROVED` が最後の行に残らないように)。needs-user を人が解決した後も、行を書き換えずに /create-task で設計レビューをやり直し、新しい行を足す(行を更新する別の経路は設けない)
- **保留の行**(ship-task の無人モードだけが書く。改行を含まない 1 行。括弧は ASCII。節の末尾に足す): `- **保留**(ship-task・YYYY-MM-DD): <停止条件> — <人が次にすること>`
  - 照合パターン(`grep -E`): `^- \*\*保留\*\*\(ship-task・[0-9]{4}-[0-9]{2}-[0-9]{2}\): `
  - `<停止条件>`: 対話点番号(`[SDUG][0-9]+`。../../ship-task/references/unattended-mode.md §4 の表の `#`)で始め、直後は空白か `:`。取り出しパターン(`grep -oE`): `^- \*\*保留\*\*\(ship-task・[0-9]{4}-[0-9]{2}-[0-9]{2}\): [SDUG][0-9]+`。`loop.sh` は、最後の保留の行からこれで番号を取り出す(`G1` の保留が続いたら止まる — ../../ship-task/references/loop.md §6)
  - 書く手順(保留の手順)と「人が次にすること」の例は ../../ship-task/references/unattended-mode.md が正本
- **記録あり**: 節の中で、空行・テンプレートの説明文(`{…}` の行)・設計レビューの行・保留の行を除いた行が 1 行でもある(見出し・段落・表・字下げした行も数える)。do-task の再開判定と base-commit.md の新規着手の条件 ② が使う。保留の行を数えないのは、do-task より前(ship-task の Phase 2)で止まった周が書く保留の行で、新規着手の条件 ② と再開判定の (C) を崩さないため
- **本文ダイジェスト**(設計レビューの行の `本文` と、無人モードの照合に使う。算出は `python3 {create-task の}scripts/task-digest.py <パス | ->` で、`-` なら stdin を読む。exit 0 = stdout に値 / 1 = 算出できない〈理由を stderr〉/ 2 = 使い方の誤り)
  - コードフェンス: 行頭の空白 3 個以内に続く ```` ``` ```` か `~~~`(3 個以上)で開き、同じ文字が同じ数以上並ぶ行(後ろは空白だけ)で閉じる。開きと閉じの行もフェンスの中に数える。閉じないまま末尾に達したら、そこまでがフェンスの中。フェンスが効くのは、`## ` の見出しの判定・除外 1 の行の判定・空行を落とす正規化・チェックボックスの正規化の 4 つ。フェンスの中の行は、見出しにも除外 1 の行にも当たらず、空行も落とさず、`- [x]` も書き換えない
  - 対象: タスク MD 全体から、次の 2 つを除いたもの
    - 除外 1: 最初の `## ` の見出しより前にある行のうち、`> **ステータス**:`・`> **基準コミット**:`・`> **無人実行**:` で始まる行(do-task・人が承認の後に書き換える行)。`# ` の見出しは任意で、見出しの無い本文(Issue 本文)でも同じ定義で働く
    - 除外 2: 追加修正記録の節。`## 追加修正記録` の見出し行から、次の `## ` の見出しの前まで。節の中の行は、フェンスの中か外かに関わらず、すべて外す
  - 正規化(この順): 先頭の BOM を除き、改行(CRLF・CR)を LF に揃える / 各行の末尾の空白(半角スペースとタブ)を削る / フェンスの外の空行(空白だけの行を含む)を落とす / フェンスの外の行頭(字下げは保つ)の `- [x]`・`- [X]` を `- [ ]` にする
    - フェンスの外の空行を落とすのは、除外 1 の行を空行を挟んで足しても値が変わらないようにするため。フェンスの中の空行とチェックボックスをそのまま残すのは、期待出力の空行や `- [x]` を書き換える変更を検出するため
  - 値: 残った行を LF で連結した文字列(末尾に改行を付けない)を UTF-8 で sha256 し、先頭 16 桁(小文字の 16 進)を `sha256:` に続けた形
  - 算出できない: フェンスの外の `## 追加修正記録` の見出し行が、ちょうど 1 つでない / UTF-8 として読めない / ファイルが読めない
  - 検出できるのは「承認後の本文の変更」と「無人の周の中の変更」まで。署名ではない(行も本文も、タスク MD を書ける者なら書ける)。除外 1 の 3 種の行と追加修正記録の節は、書き足し・書き換え・削除を検出しない(受け入れる限界は ../../ship-task/references/unattended-mode.md)
- **無人実行のメタ行**: 書式は `> **無人実行**: 可`。最初の `## ` の見出しより前(ヘッダ)に置く。照合パターン(`grep -E`): `^> \*\*無人実行\*\*: 可[[:space:]]*$`(`[[:space:]]` にしたのは、CRLF の行の `\r` にも一致させるため)
  - 付けるのは人。create-task は、ユーザーが求めたときだけ付ける。除外 1 の対象なので、付けても設計レビューのやり直しは要らない
  - メタ行を付けるタスク MD は、コードフェンスの中にチェックボックス形の行(`- [ ]`・`- [x]` とも)を書かない。do-task の集計はフェンスの中の行も数えるため、無人では完了できない。`- [ ]` の見本は Phase 7 の手順 1 で印を求められるが、フェンスの中に印を付けると本文ダイジェストが変わる。`- [x]` の見本は、着手の段階で新規着手の条件 ①(`- [x]` が 1 つも無い)を崩し、再開判定の (B) も成り立たせるので、『基準不明』になる(無人では保留。限界の詳細は ../../ship-task/references/unattended-mode.md)
- **作成日の行**: 書式は `> **作成日**: YYYY-MM-DD`(ヘッダ)。照合パターン(`grep -E`): `^> \*\*作成日\*\*: [0-9]{4}-[0-9]{2}-[0-9]{2}`。見るのはヘッダ(最初の `## ` の見出しより前)の中だけ。使うのは `loop.sh` の並び(作成日の古い順。作成日が無いタスクは最後 — ../../ship-task/references/loop.md §3)
- **候補の書式**(`候補_{名}.md`。発見元の候補モードが書く、設計書の手前の候補。書き出しの手順・指摘キーの文法は [candidate-mode.md](candidate-mode.md)。採用すると `進行中_` になる — ../SKILL.md の「採用の経路」)

  ```markdown
  # {名}

  > **ステータス**: 候補
  > **作成日**: YYYY-MM-DD
  > **発見元**: {data-audit | refactor}({呼び方。例 /data-audit --candidates --quick})
  > **指摘キー**: {キー}
  > **発見時点**: {HEAD の sha の先頭 12 桁}
  > **深刻度**: {重大 | 高 | 中} / **確度**: {確実 | 要確認}      ← data-audit のとき
  > **スコア**: {N}                                                  ← refactor のとき
  > **見送り**: YYYY-MM-DD — {理由}                                  ← 人が付ける

  ## 指摘
  ## 根拠(発見時点の path:line)
  ## 出典(観点 ID・メトリクスなど、発見元の根拠)
  ## 修正方針(案)
  ## 人が確かめること(確度が要確認のときだけ)
  ```

  - 書かないもの: 無人実行のメタ行・チェックボックス形の行(`- [ ]`・`- [x]`。フェンスの中も)・`## 追加修正記録`・設計レビューの行(`loop.sh` の実装モードが拾う形にしない — 採用は人)
  - 名: create-task の命名(内容を表す簡潔な日本語)に従い、何を直すかの言い方にする(採用の後もタスク名として通るように)。先頭に発見元の接頭(`監査-`・`リファクタ-`)を付ける。`-` で始めず、../../ship-task/references/loop.md §3 の文字の制限を満たし、`git check-ref-format --branch 'task/{名}'` を通す。同じ task_dir の既存のどの状態名の `{名}` とも重ねない(重なり、指摘キーが違えば `-2`・`-3` を付ける。キーも同じなら重複として書かない — candidate-mode.md)
  - ヘッダ: 最初の `## ` の見出しの行より前の行。コードフェンスの中の行は見出しに数えず、メタ行としても読まない(フェンスの定義は下の「本文ダイジェスト」と同じ)
  - 本文は単体で読める形にする(`.claude/reviews/` のパスを根拠にしない — design §5-18 ①)。機密の値を書かない(`secret_paths` のファイルを読まない。値ではなく場所で書く)
- **候補のメタ行**(照合パターンは `grep -E` と Python の `re` で同じ字面で使える。ヘッダの中だけを見る。読み取りは `python3 {create-task の}scripts/candidate-keys.py` — 本文ダイジェストと同じく、改行と行末の空白を揃えてから照らす)
  - 発見元: `^> \*\*発見元\*\*: (data-audit|refactor|stack-research|reflect-decisions)( |\(|$)`
  - 指摘キー: `^> \*\*指摘キー\*\*: (.+)$`。値は捕捉の組を正規化したもの(文法と正規化は candidate-mode.md)。発見元が書く候補は 1 行。複数行になるのは、人が複数の候補を 1 つのタスクにまとめて行を写したときと、採用の分割のときだけ
  - 見送り: `^> \*\*見送り\*\*: ([0-9]{4}-[0-9]{2}-[0-9]{2} — .+)$`。値は捕捉の組の文字列。区切りは em ダッシュ `—` だけ。人が `候補_` のヘッダに足して commit する(PR の上でも、merge の後でもよい)。発見は、この指摘キーを以後積まない。状態名は `候補_` のまま(消すと記録が残らず、同じ指摘が後の晩にまた出うる)
  - 見送りの書式違い: ヘッダの中で `> **見送り**:` で始まるのに、上のパターンに合わない行(`-`・`―` で区切ったなど)。candidate-keys.py が problems(`skipped-malformed`)に出す。採用は、見送りと同じく止める
- **採用の引き継ぎ**(採用の経路で `候補_` を `進行中_` に改名した後、このテンプレートで全体を書き直すとき)
  - 作成日は採用日(`loop.sh` の並びはこれを使う)。発見日は発見元の行の末尾に ` — 発見 YYYY-MM-DD` として併記する
  - 発見元・指摘キーの行はヘッダにそのまま引き継ぐ(以後の重複の判定が全状態のヘッダを見るため。本文ダイジェストの対象になる)。分割したときは、指摘キーの行を全部の MD に写す
  - 無人実行・見送り・深刻度と確度・スコアの行は引き継がない(無人実行のメタ行は、ユーザーが求めたときだけ付ける — 上の「無人実行のメタ行」)
  - 候補の指摘・根拠・修正方針(案)は、概要・現状分析(再確認した path:line)・技術的考慮事項に取り込む
- **発見の記録の節**(任意。採用したときだけ。`## 追加修正記録` より前に置く): 候補の「指摘」「根拠」「出典」の節だけを写す。見出しは `### ` に下げ、根拠の見出しには発見時点を入れる(`### 根拠(発見時点 {sha} の path:line)`)。チェックボックス形の行を持ち込まない。確度の行と「人が確かめること」の節は写さない(ship-task の Phase 2 の 1 は本文全体の「要確認」などを探すので、解いた質問を残さない)

## 短縮記録 — `--compact`
