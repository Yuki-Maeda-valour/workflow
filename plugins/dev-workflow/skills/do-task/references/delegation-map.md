# 委託の解決表(役割語 → 実行バックエンド)

skill 本文が**役割語**で書いた委託を、**どのバックエンドの何で実現するか**に対応づける仕様。委託を行う全 skill(do-task / create-task / update-doc / reflect-decisions / init-project / data-audit / stack-research)の委託箇所から参照する。

> **このファイルが委託の解決の唯一の正本**(役割語の一覧・派生名の体系・役割語だけで表現できない属性軸・解決順・ホスト = Claude Code での解決・解決できないときの縮退)。
> `docs/design.md` §5 前文・§6・§7-5 は**方針(なぜ役割語 + 解決表か・なぜ順序固定か)だけ**を持ち、各 SKILL.md / review-protocol.md / README は**再掲せずここを参照する**。
> **分担(ここでは再掲しない)**: ③ CLI の**手順の契約**(判定順序・終了コード・既定ランナー表・読み取り専用の保証範囲・ログ規約・機密ガード)と**③ 宣言時の枡ごとの置換可否・内蔵の維持範囲**は [external-runners.md](external-runners.md) が正本(後者は同 §8「編成規則」)。**体数 → 枡名の割り当ては本表 §2 (a)**、**枡ごとの狙い(観点の割り当て)と起動手順は [review-protocol.md](review-protocol.md)** が持つ。③ の**宣言方法・信頼モデル・implementer の扱い**は design §7-2 が正本(design §7-5 前文の分担)。
> **このファイルは「委託の語」(design §7-7)の検査対象外**である — 役割語をホスト固有の機構へ解決することがこのファイルの役割であり、ホスト固有語を意図的に持つため。[external-runners.md](external-runners.md) も同じ理由で検査対象外(③ CLI と ① 内蔵の相互作用を説明する契約本文にホスト固有語を 2 箇所持つ)。**除外集合の正本は design §7-7** であり、ここでの宣言は補助に留まる。
> **検査対象外は「何を書いてもよい」ではない**: モデルエイリアス名だけは**自ら 0 件に保つ**(design §3 の「解決表はエイリアスの一覧を持たず、指定方法だけを持つ」)。
> 委託の解決を変えるときは、このファイルと design §5 の併記(v4.0.0 までの期間限定)の 2 点を直す。**先にこのファイルを直し、design を追随させる。**

## 1. 役割語の一覧

`researcher` / `implementer` / `reviewer` / `checker`

| 役割語 | 何を委ねるか |
|---|---|
| `researcher` | 調査・探索(読み取りのみ) |
| `implementer` | 実装(編集とコマンド実行を伴う) |
| `reviewer` | 独立レビュー(読み取りのみ) |
| `checker` | 生成物の規約・観点検証(読み取りのみ) |

- **`team-lead` はこの一覧に含めない** — 委託先ではなく**委託する側(セッション自身)の呼称**である(design §7-5)。委託先の名前として `team-lead` を使わない
- **一覧の出自**: 既存 skill が使う役割から採録したものであり、出典の決定録は一覧を定めていない(design §7-5)。役割語を増やすときはこの表に足す

## 2. 派生名は「役割語 + サフィックス」

同じ役割の委託先が複数あるときは、役割語にサフィックスを足す。**サフィックスの系統は次の 3 つだけ**とし、系統をまたぐ新設をしない。

| 系統 | 形 | 値 | 意味 | ホスト非依存か / 解決表側の解決か |
|---|---|---|---|---|
| (a) 固定枡 | `reviewer-<枡>`(`alt` のみ順序添字を許す) | `internal` / `strong` / `alt` | レビュー編成の枡(**体数別の割り当ては下の小節**)。**能力帯はここで表す** — `internal` = ホストのモデルを継承 / `strong` = 利用可能な最上位 / `alt` = 上位〜標準の別モデル | **枡の意味はホスト非依存**。各枡へ実際に何を割り当てるかが解決表側の解決(§3 の軸 3) |
| (c) ランナー名 | `reviewer-<ランナー名>` | 既定表にあるランナー名、および **`--runners` でユーザーがセッション内に明示指定した名前**(既定表外。この経路では**読み取り専用の保証はユーザー責任**) | 外部ランナーを追加枡として足す | **③ の解決**。名前の集合と既定表外の受け付け条件は [external-runners.md](external-runners.md) §1・§4、枡の扱いは同 §8 |
| (d) 観点 | 次の 3 形のみ — ①`<役割語>-<観点>` ②**観点語のみ**(役割語の省略を許す) ③**`<観点接頭辞>-<観点>`**(**既存の `scan-*` 4 名に限る。新設では使わない**) | 観点を表す語(`exposure` / `authz` / `db` / `efficiency`)。既存 4 名は ③ の形で、観点接頭辞 `scan`(= 読み取り専用の並列調査群の総称)を冠する | 同じ役割を観点別に並列展開したもの。読み取り専用の並列調査は実体として `researcher` の派生 | **ホスト非依存**(観点はタスク側の関心事) |

- **(d) の既存実例 `scan-*` 系 4 名は ③ の形に該当し、本規約に適合する — 改名しない**(結論)。役割語を省いても、読み取り専用の並列調査であることから役割は `researcher` に一意に決まる。移行タスクは名前を変えず、解決の参照先を本表へ向けるだけでよい。**新しく観点派生を作るときは ① の形を使う**(③ は既存 4 名限りで、観点接頭辞を新設しない)
- **`scan-exposure` を据え置き `reviewer-{モデル}` を移行対象とする切り分けの理由**: design §5-3 の `name` 例示行には両者が並んでいるが、**移行で消えるのは `reviewer-{モデル}` 側だけ**である。後者はサフィックスに**モデルエイリアス名**が入るため design §3 の「解決表はエイリアスの一覧を持たない」に直接抵触し、エイリアスはモデルの世代交代で陳腐化する(§5-4)。前者の接頭辞は**観点群の総称**でホスト固有の語を一切含まないため、そもそもホスト非依存化の対象にならない
- 観点の割り当ては [review-protocol.md](review-protocol.md) が持つ

### (a) 体数 → 枡名の割り当て

**体数の解決は本表の外**: 体数は各 skill の引数・profile に従う(**ホスト非依存**。do-task は `--reviewers` 引数 → profile の `features.reviewer_count` → 既定 1)。`--reviewers` を持たない skill は skill 本文の要請(「能力帯の異なる 2〜3 体」等)を体数とする。**`features.review_models` の要素数はモデル指定枠の数**にあたり、継承枠を置く編成ではそれに継承枠を加えた数が体数になる(要素数そのものを体数と読まない)。**本表が定めるのは体数から枡名への写像だけ**で、体数そのものは持たない。外部ランナーは体数に含めない(内蔵の数で数える)。

**枠は体数から逆算する**(枡集合を一意にするための決着):

1. **継承枠(モデルを継承する枠)を置くかは呼び出し側 skill の要請に従う** — 本表が体数から一律に決めない(決めると編成の実質が変わる)。**次のうち ③ の宣言に関する最後のブレットが他より優先し、残りは上から最初に当たったものを採る**
   - **1 体構成(③ の宣言なし)**では素の `reviewer` が継承枠にあたる
   - **内蔵継承枠を含む 3 体構成**(do-task のレビュー編成。[review-protocol.md](review-protocol.md))では `reviewer-internal` を置く
   - **継承枠を持たない複数モデル編成**(「能力帯の異なる 2〜3 体」を全枠モデル指定で組む skill)では**置かない**
   - **③ が宣言されているときは体数に関わらず `reviewer-internal` を置く(このブレットが最優先)** — **継承枠なし編成でも置き、そのぶん明示指定枠を 1 つ減らす**。内蔵レビュアーを全滅させない要請([external-runners.md](external-runners.md) §8・design §7-2)は編成の都合より強いため
2. **要請体数 − 継承枠 = モデルを明示指定する枠の数**
3. その枠へ `features.review_models` の**先頭から順に**割り当てる(リストが無ければ実行時に能力上位から選ぶ)。**1 枠なら `strong` / 2 枠なら `strong` + `alt` / 3 枠以上なら `alt` に順序添字**(添字なしが 1 番目、以降 `reviewer-alt2` / `reviewer-alt3`)
   - **明示指定枠が 0 になるのは継承枠だけの構成**(体数 1・③ の宣言なし / ③ 宣言 + 内蔵 1 体)。このとき `strong` は生じない
4. **不変条件: 明示指定枠の数 + 継承枠 = 要請体数。** これを超える割り当てをしない

| 編成 | 使う枡 | `review_models` から消費する要素数 |
|---|---|---|
| 1 体(③ の宣言なし) | **素の `reviewer`**(枡名を付けない。**継承枠**) | **0**(消費しない) |
| **継承枠なし**の N 体(N ≥ 2) | `strong` + `alt` + `alt2` …(**N 枠**) | **N**(リストを使い切る) |
| **継承枠あり**の N 体(N ≥ 3) | `internal` + `strong` + `alt` …(継承枠 1 + **N−1 枠**) | **N−1** |
| ③ の宣言あり(内蔵 N 体)**— 上の行より優先** | **`reviewer-internal` を必ず置く**(内蔵 1 体でも素の `reviewer` にしない。継承枠なし編成でも置く)+ 残り **N−1 枠** | **N−1** |

- **1 体は素の `reviewer`(Explore・モデル継承)とし、`review_models` を消費しない**(`reviewer-strong` にしない)。宣言された値を使わなかったことを報告する。**理由**: 既存契約([review-protocol.md](review-protocol.md) の 1 体構成 / do-task Phase 6)が 1 体を読み取り専用種別のモデル継承と定めており、ここでモデルを明示指定すると軸 1 の決定順 ③ により general-purpose へ寄る = **既定経路(`--reviewers` / `features.reviewer_count` の既定 1)の種別が変わる**(手順 1 の 1 行目と同じ「写像で編成の実質を変えない」判断)。しかも読み取り専用種別にモデル指定ができるかは未検証なので、**既定経路を未検証の前提に依存させない**(下の根拠ブレットと同じ判断)
- **継承枠はリストの要素を消費しない**(モデル継承であって能力帯の選択ではないため)。「利用可能な最上位から能力順に選ぶ」対象の枠は `strong` / `alt` 系だけ
- **打ち切りと落とす端**: **`review_models` の要素数が枠数(要請体数 − 継承枠)を超える分**は打ち切る。落とすのは**能力帯の下位側**(リスト末尾)で、`strong` に当たる先頭要素は必ず残す(design §5-9 の「最上位を必ず含める」)。**打ち切ったことを報告する**(サイレント切り捨て禁止)。報告には**設定ミスではなく編成の差である旨**を添える — 継承枠を置く 3 体構成に 3 要素のリストが与えられた場合、消費するのは先頭 2 要素で 3 要素目は打ち切りになる(継承枠なしの 3 体編成なら 3 要素とも使い切る)
- **継承枠だけの構成では `review_models` を消費しない**(③ 宣言 + 内蔵 1 体 = `internal` のみ / ③ 宣言なしの 1 体 = 素の `reviewer`)。宣言された値を使わなかったことを報告する
- **design §5-9 の「能力帯の異なる 2〜3 体」の数え方**: **能力帯の撃ち分けは `strong` / `alt` 系の枠数で数え、継承枠(`internal` / 素の `reviewer`)は数に入れない**(能力帯が不定であるため)。よって `internal` + `strong` + `alt` の 3 体構成は「能力帯の異なる 2 体 + 継承枠 1 体」として §5-9 の下限を満たす
- **③ 宣言時に `internal` を必ず置く理由**: 編成が「内蔵 N + 外部 M」になり、内蔵枠が**維持されている枠として識別可能**である必要があるため。**③ 宣言時の枡ごとの置換可否・内蔵の維持範囲**は [external-runners.md](external-runners.md) §8 が正本
- **2 体は現状の入口では到達不能**: `--reviewers` と `features.reviewer_count` はいずれも **1 か 3 のみ**を受け付ける(design §4 の profile スキーマと do-task の `argument-hint`)。design §5-9 は「能力帯の異なる 2〜3 体」を認めているため写像としては定義しておくが、**入口の受け付け値の拡張は別 issue**(本表の変更では届かない)

### (b) 能力帯サフィックスは独立系統として持たない

能力帯は (a) の固定枡が既に抽象語で表しているため、**能力帯だけを表すサフィックス系統を別に立てない**。既存 skill にある `reviewer-{モデル}` 形(サフィックスにモデルエイリアスが入る形)は **(a) の `strong` / `alt` へ寄せる**。理由は 2 つ:

1. **design §3 との両立** — 「解決表はエイリアスの一覧を持たない」。`reviewer-{モデル}` を派生名の系統として認めると、委託先の名前の一部としてエイリアス名が本文に現れる
2. **(c) との形の衝突の解消** — `reviewer-{モデル}` と `reviewer-{ランナー名}` はどちらも `reviewer-<語>` であり、**サフィックスを見ても能力帯を指すのかランナーを指すのか区別できない**。(a) へ寄せれば名前にエイリアス名が入らなくなり、派生名は `reviewer-<枡>` と `reviewer-<ランナー名>` の 2 種に整理される

**未決(ここだけ)**: 固定枡 3 語(`internal` / `strong` / `alt`)で表せない**新しい能力帯**が必要になった場合の拡張規則(同じ能力帯を複数体に増やす場合は上の順序添字で決着済みなので未決に当たらない)。枡を足すと [review-protocol.md](review-protocol.md) の構成表と [external-runners.md](external-runners.md) §8 の編成表の両方に反映が要るため、規則を決めてから足す。

## 3. 役割語だけで表現できない属性軸

役割語と派生名で表せない要請は次の **10 軸**で持つ。「正本の所在」列は、**値をこの表が持つのか、他の正本を指すだけなのか**を行ごとに示す。

| 軸 | ホスト非依存の要請 | Claude Code での解決 | 正本の所在 |
|---|---|---|---|
| 1. 読み取り専用性 | 調査・レビューは読み取りのみ、実装は編集可。両者を混ぜない(**編集するかどうかの軸**であり、必要なツールは軸 9・モデル指定は軸 3 で別に見る) | **種別選択の決定順(ここに集約する。上から最初に当たったものを採る)** — ①編集・コマンド実行を伴う → general-purpose ②読み取りのみだが**追加ツール**(Web 取得等)が要る → general-purpose + 指示に「読み取り専用。ファイルを編集しない」を明記 ③読み取りのみで**モデルを明示指定する** → general-purpose + 同じ明記 ④それ以外 → **Explore**。②③ で general-purpose を使う場合、軸 1 の要請は指示で担保する | 要請は design §5-13。**種別名と決定順は本表**(軸 3・軸 9 はこの決定順を参照するだけで、独自の種別選択を持たない) |
| 2. 並列性 | 複数の委託を同時に走らせる / 逐次でよい | 内蔵は**単一メッセージ内で複数の Agent を起動**する(逐次起動しない) | 内蔵の手段は**本表**。③ 側の実現手段は [external-runners.md](external-runners.md) §8 が契約として持つ(**ここには写さない**) |
| 3. モデルの能力帯 | **複数枠**(レビュー編成のようにモデルを明示指定する枠が 2 つ以上あるもの)では最上位 / 上位 / 標準を撃ち分け、最上位を必ず含める(**③ が宣言されているときは軸 10 が優先する**)。**単一枠**(implementer のように **§2(a) の枡集合に属さず**、モデルを明示指定する枠が 1 つだけのもの)では**標準の能力帯**を選ぶ。**継承枠だけの構成**は明示指定枠が 0 なのでどちらにも当たらない(§2(a)) | Agent ツールの `model` 引数でエイリアスを指定する。解決順は profile の `features.review_models` / `features.implementer_model` → **実行時に指定可能なエイリアスを確認**(design §3・§5-4・§5-9)。**指定方法だけを持ち、エイリアス名の一覧は持たない**。**枡ごとの種別は軸 1 の決定順で決まる** — モデルを明示指定する枠(`strong` / `alt` 系)は決定順 ③ に当たるので general-purpose、モデル継承の枠(`internal` / 素の `reviewer`)は ④ に当たるので Explore | 指定方法は**本表**。**種別選択は軸 1 が正本**(ここは決定順を適用した結果を示すだけ。根拠は下のブレット)。値(どのエイリアスが在るか)は**実行時の確認結果**が正本で、profile が優先を与える |
| 4. 宛先識別 | 委託先を**宛先として識別可能にする**(名前が無いと双方向連携の経路が塞がる) | Agent 起動時に `name` を必ず付ける。`name` は半角英数・ハイフン・アンダースコアのみ(日本語は使えない)。**チームの明示生成 API(TeamCreate / TeamDelete)は使わない** — 廃止方針であり、セッション単位の暗黙チームで足りる | 要請は design §5 前文。**`name` の引数名・文字種規則と、明示生成 API を使わない規定は本表** |
| 5. 完了後の再依頼 | 完了した委託へ差し戻し・再レビューを依頼する(文脈を保つ) | **同じ `name` へ `SendMessage`**(再スポーンしない)。宛先が失われている(`ListAgents` に無く `SendMessage` が失敗する)ときだけ新規起動へフォールバック | 用途の定義は design §5-17 の用途 ①。**API は本表** |
| 6. 走行中の問い合わせ・前提是正・中止 | 走行中の委託に状態を尋ね、前提の誤りを訂正し、不要になった委託を中止する | `SendMessage` で送る(状態問い合わせ・前提是正・中止はいずれも同じ経路) | 用途の定義は design §5-17 の用途 ②③、待機目安と手順は [review-protocol.md](review-protocol.md) の M1〜M4。**API は本表** |
| 7. 委託先の生存確認・一覧 | 委託先が生きているかを確かめる(問い合わせの前提) | `ListAgents` で一覧を取る | 手順(M1)は [review-protocol.md](review-protocol.md)。**API は本表** |
| 8. 段階判定 | フル / 標準 / 最小のどれで走るかを**着手時にツールの実在で判定**する(推測しない・ユーザーに聞かない) | フル = `Agent` + `SendMessage`(+ `ListAgents`)が実在 / 標準 = `Agent` は実在するが `SendMessage` が無い / 最小 = サブエージェント機構が無い | 段階の定義・段階ごとの縮退の中身は design §5-17。**判定手段(どのツールの実在を見るか)は本表** |
| 9. 必要なツール・権限 | 委託先が仕事に要するツール(Web 取得・コマンド実行など)を満たす。**軸 1(編集するか)とは直交する関心事** | **軸 1 の決定順に従う** — 追加ツールが要る委託は決定順 ② に当たるので general-purpose + 指示に読み取り専用を明記。**この軸は独自の種別選択を持たない**(モデルを明示指定する枠は ③ で先に決まる) | 要請(どの委託にどのツールが要るか)は**本表**。**種別選択は軸 1 が正本** |
| 10. ベンダー多様性 | 複数ベンダーのモデルで見るか、同一ベンダー内の能力帯差で見るか | ③ が宣言されていないときは軸 3(能力帯)に従う。**③ が宣言されているときはベンダー横断の多様性を同一ベンダー内の能力帯差より優先し、各社の最上位級を組み合わせる**(製品名・版数を書かず実行時に選ぶ)。利用不可のときは内蔵のみの編成へ縮退し理由を報告する | **優先規則は本表**。③ の起動手順と枡ごとの扱いは [external-runners.md](external-runners.md)、宣言方法は design §7-2 |

- **軸 4 と軸 5〜7 の依存関係**: 宛先識別(軸 4)が成立しないと、再依頼・問い合わせ・生存確認(軸 5〜7)は成立しない。design §5-17 の**標準段階**(`Agent` は実在するが `SendMessage` が無い段階)がまさにこの状態で、委託自体はできるが宛先が存在しないため要請が生じない
- **決定順 ③(モデルの明示指定で general-purpose に寄せる)を置く根拠**: レビュアーはいずれも読み取りのみで足り追加ツールも要らないため、③ が無ければ全枠が ④ の Explore になる。**分岐の実際の理由はモデルを明示指定するか継承するか**であり、これを ③ として決定順に組み込んだ。結果は「明示指定する枠は general-purpose + 読み取り専用の明記、継承枠は Explore」で、これは [review-protocol.md](review-protocol.md) の既存契約に一致させた結論で、**読み取り専用種別にモデル指定ができるかはこのリポジトリの記録では未検証**のため、裏取りせずに「全枠を読み取り専用種別へ寄せる」結論は採らない(design §5-11 の実コード優先・推測禁止)。寄せる場合はホストの事実として **design §7-3(前提とする外部事実)に出典付きで記録してから本表を直す** — **移行タスクの判断で変えてはならない**
- **自ホスト判定は軸に立てず参照にする**: ホスト自身と同じ CLI を Bash から起動しないこと(Claude Code なら `claude -p` / `claude --print` の Bash 起動を禁止)は design §5-5 の原則であり、判定手段は [external-runners.md](external-runners.md) §3 の判定 2 が契約として持つ。二重管理を作らないため、ここでは参照に留める

### 能力帯の抽象語を定義するのはこの表

`internal` / `strong` / `alt` の意味(§2 (a))と、能力帯 → エイリアスの指定方法(軸 3)を**定義するのはこの解決表**であり、[review-protocol.md](review-protocol.md) の構成表と [external-runners.md](external-runners.md) §8 の編成表は**消費側**である。定義と消費の向きを固定し、**消費側に定義を生やさない**(定義が 2 箇所に増えると同期漏れが起きる)。

## 4. 解決順(① ホスト内蔵 → ② MCP → ③ CLI で固定)

| 順 | バックエンド | 既定 | 有効化 |
|---|---|---|---|
| ① | ホスト内蔵のサブエージェント(Claude Code = Agent ツール) | **有効**(既定はこれだけ) | 常に |
| ② | MCP ツール | 無効 | **有効化手段が未定**(§5) |
| ③ | CLI 起動(外部ランナー) | 無効 | 宣言時のみ(**宣言方法は design §7-2 が正本**、手順の契約は [external-runners.md](external-runners.md)) |

- **順序は固定**。profile が宣言できるのは**各バックエンドの有効化のみで、順序は変えられない**(design §7-5)
  - **これはバックエンドの順序についての制約**である。モデル指定(`features.review_models` / `features.implementer_model`)・ランナー名(`features.runners`)・ランナー別モデル(`features.runner_models`)の profile 宣言は別で、従来どおり有効(design §3・§7-2 の信頼モデルの範囲内)
- **どのバックエンドで実行したかを報告に明記する**(design §5-9 / §5-17 の報告義務の適用)
- **③ 宣言時の枡ごとの置換可否・内蔵の維持範囲**は [external-runners.md](external-runners.md) §8 が正本(本表は**体数 → 枡名の割り当て**だけを §2 (a) で持つ)

## 5. ② MCP バックエンド(未定・未検証)

- 本節が扱うのは**委託先としての MCP** であり、**ツール接続としての MCP(design §7-6)とは別概念**
- **有効化手段は未定**であり、決まるまで既定(① のみ)から変更できない。**未検証**(返るツールの形は未確認)
- **② を有効化する profile キーは未定義であり、未知のキーを ② の宣言と解釈しない**(キー名が決まっていないため、検出条件を定義できない)
- したがって**この節の報告義務はキーが確定してから課す**: キーが定まったら「**② の有効化を宣言する profile 値は解決されない。受理して黙って落とすのではなく、無視して報告する**」(サイレント無視禁止。design §7-2 の信頼モデルが同型の事例で求めているのと同じ扱い)を適用する。それまでに ② を有効化しようとする記述を見つけた場合は、**キー未定のため解釈しなかった旨**を報告する

## 6. 解決できないときの縮退

- **兄弟参照でこのファイルに到達できない構成**(skill を 1 本だけ取り出した部分導入)では委託の解決ができない。この場合は **design §5-17 の最小段階(直列セルフ実行+機械検証)へ縮退**し、縮退したことと理由を報告する(サイレント縮退禁止)
- 探索を広げて代替を探しに行かない。**諦める側に倒す**(design §6 の共有アセット規約と同じ温度感)
- **検出手段は未定義**(別論点): 「参照先が存在しない構成では無効化して報告する」は現状すべて散文の義務であり、**存在をどう確かめるかは契約になっていない**。この解決表も同じ扱いとする
  - 併せて: `scripts/review-agent.sh` は **skill 本文 → references → スクリプト**の 2 段間接で参照されるため、部分導入で壊れる箇所が 2 つある(references に到達できない場合と、references には到達できてもスクリプトに到達できない場合)

## 7. この表の限界(**過信しない**)

この表が持つのは「**要請 → 手段の写像**」だけであり、**手段の実効性は保証しない**。

| 要請 | この表が保証すること | 保証しないこと |
|---|---|---|
| 読み取り専用性(軸 1) | 読み取り専用の種別と指示の与え方を指す | 委託先が本当に書き込まないこと(種別と指示に対するホスト側の実装を信頼している。③ 側の保証範囲は [external-runners.md](external-runners.md) §3) |
| 並列性(軸 2) | 同時に起動する手段を指す | 実際に同時実行されること(ホスト側のスケジューリングに依存する) |
| モデルの能力帯(軸 3) | 指定方法を指す | 指定したエイリアスが実行環境で利用可能であること(実行時に確認する) |
| 宛先識別(軸 4) | `name` の付け方と文字種規則を指す | `name` がセッション内で一意であること・宛先が生存し続けること(軸 7 で確かめる) |
| 完了後の再依頼(軸 5) | 宛先へ差し戻しを送る手段を指す | 委託先が受け取って文脈を保ったまま再開すること(宛先が失われていれば新規起動へ落ちる) |
| 走行中の問い合わせ・前提是正・中止(軸 6) | **送達**の手段を指す | 委託先が読んで従うこと・**中止が即時に効くこと**。中止を伝えても走り切る場合があるため、結果を黙って捨てず扱いを報告する(design §5-17 の用途 ③) |
| 委託先の生存確認・一覧(軸 7) | ある時点の一覧を取る手段を指す | **一覧の鮮度** — 取得後に宛先が失われることは防げない |
| 段階判定(軸 8) | どのツールの実在を見るかを指す | **ツールの実在は起動の成功を保証しない**(権限・クォータ・無応答で失敗しうる)。③ 側にも「存在確認だけでは足りない」という同型の知見がある([external-runners.md](external-runners.md) §3) |
| 必要なツール・権限(軸 9) | 種別の選び方と読み取り専用の明記を指す | 選んだ種別でそのツールが実際に使えること(ホスト側の可用性・権限に依存する) |
| ベンダー多様性(軸 10) | ③ 宣言時にベンダー横断を優先する規則を指す | 宣言したベンダーが実際に使えること(未導入・認証切れ・レート制限では内蔵のみの編成へ縮退する。理由の報告は必須) |

**表に行があっても、その要請自体を満たせないホストは存在する。** 行の存在は「どのホストでも実現できる」ことを意味しない — 満たせないときは §6 の縮退(design §5-17 の段階)へ落ちる。

なお「**ホスト固有だから吸収しない**」という切り方はしない。ホスト固有の解決を 1 箇所に持つことがこの表の存在意義であり、並列性(軸 2)・段階判定(軸 8)もホスト固有だが軸として吸収している。
