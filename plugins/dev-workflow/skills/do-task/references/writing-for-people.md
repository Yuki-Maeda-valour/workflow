# 人が読む文の書き方

> 人が読む文(会話の応答・質問・PR と Issue の本文・作る文書・コミットメッセージ)の書き方の正本。
> - 読むとき: 人が読む文を書く前。全 skill の `## 原則` がこのファイルを指す
> - 置き場: do-task が持ち、ほかの skill の SKILL.md は `../do-task/references/writing-for-people.md` で引く
> - プロジェクト固有の言葉は、プロジェクトの用語集(既定は `doc/01_overview.md`)が正本。このファイルには書かない
> - 2 節の 8 項目は同じ文で、3 節の優先順位は同じ順で、init-project の [AGENTS.md の雛形](../../init-project/templates/AGENTS.md.template) の「応答の書き方」節にコピーしてある(雛形は、コミットメッセージ・用語集・字面を変えない行の要点も持つ)。2 節・3 節を変えるときは、雛形も直す
> - 決まりを変えるときは、先にこのファイルを直す。design §5-25 は要点だけを持つ

## 1. 対象と効かせ方

人が読む文の種類ごとに、わかりやすさの決まり(2 節)と口調(6 節)をどこまで当てるかを決める。

| 種類 | わかりやすさの決まり | 口調 |
|---|---|---|
| 人との会話の応答(報告・説明・質問と選択肢・完了報告) | すべて | 当てる |
| 完了報告のコピー用の枠(8 節) | すべて | 当てない。段落の印も付けない |
| Issue 本文・PR 本文・作る文書(`doc/`・README・決定録・タスク MD の人が読む節〈概要・完了条件・スコープ外〉) | すべて | 当てない |
| コミットメッセージ・PR タイトル・Issue タイトル | プロジェクトの規約(言語・接頭辞・長さ)が先。効かせるのは 1・2・6・7 だけ | 当てない |
| 障害やセキュリティの急ぎのやり取り | すべて(失敗と危険の知らせは省かない) | 当てない |
| AI への依頼文と、その返答(報告・指摘 JSON) | 正確さだけ(決まった書式を守る) | 当てない |

- どの種類でも、字面を変えない行と語(5 節)は字面どおりに書く

## 2. わかりやすさの決まり

人が読む文すべてに効かせる(範囲は 1 節の表)。口調の正本がどれでも常に効く。

1. 結論を最初に書く
2. 1 文に 1 つのことだけ書く。短く切る
3. 箇条書きを中心にする
4. 専門用語・内部の言葉は使わない。使うときは、その会話(その文書)で初めて出すときに平易な言い換えを添える。コードの名前・コマンド・パスは `` ` `` で囲んでそのまま書く(字面を変えない行と語は除く)
5. 人にしてほしいこと(答え・操作)があるときは、最初か最後に分けて書く
6. 「対応する」「整理する」のような、何をしたか分からない言葉を避ける
7. 数字と事実で書く。確かめていない事実は「未確認」と書き、推測は推測と分かるように書く
8. 長い説明は求められたときだけ書く

言い換えの言い方は 4 節の表、字面を変えない行と語は 5 節に従う。

## 3. 優先順位

決まった書式 > 正確さ > 簡潔さ > 口調

- 決まった書式は、5 節の字面を変えない行と語を指す
- 短くするために事実を落とさない
- 失敗と危険の知らせは、短くしても省かない

## 4. 言い換え表

人に出す文で 1 列目の言葉を使うときは、その会話(その文書)で初めて出すところで 2 列目の言い方を添えるか、2 列目の言い方に置き換える。

- 表は、このプラグインの内部の言葉、開発の言葉の順に並べる
- 人に出す報告・質問・選択肢・Issue と PR の本文で、番号が理由・判定・指摘そのものになるときは、「番号: 中身」の形で一言添える(例: `G3: 無人の前提を欠く`、`S4: 承認の後に本文が変わった`)。対象は D・S・U・G・M・H の番号、決定 N、軸 N、①〜⑳・条件 ③、§N-N など。S・D・U・G の中身は、その周で当たった理由を一言で書く。[unattended-mode.md](../../ship-task/references/unattended-mode.md) §4 の表の行を目安にする。S4 なら、当たった続行判定の項目の名前から書く(例: `6 本文の照合` → `承認の後に本文が変わった`)。参照先を示すだけの番号(「正本は loop.md §4」「#107 の H48」)と、手順の本文・相互参照の番号は残してよい
- 補足に「決まった語」とある言葉は、5 節の (ii) のとおり字面を変えずに使い、2 列目の説明を添える(言い換えない・訳さない)
- 補足が「置き換える語」で始まる言葉は、会話でも文書でも使わない。初めて出す所に限らず、2 列目の頭の言い方に置き換える。名前(見出し・太字の項目名)に入っていれば、名前のほうを変える。dev-workflow の開発リポジトリでは、design §6 の「置き換える語」と「文書の中で置き換える語」の 2 行が正本で、`validate.py` の検査 11 が文書の中を止める。会話は検査されないので、書く前にこの表で確かめる
- 補足が「使わない言い方」で始まる言葉は、人に出す文(会話の報告・質問・Issue と PR の本文)で、補足に書いた意味で使う所だけに当て、2 列目の言い方に置き換える。同じ字面を別の意味で使う所(モデルを指定する仕組みの「モデル指定」など)と、名前には当てない。検査は無いので、書く前にこの表で確かめる
- 「縮退」は意味が 4 つある。無人の周の結末の値のときだけ字面を変えずに使う。ほかの 3 つの意味は、2 列目の言い方に言い換える。どれにも当たらないときは、何が起きるかをそのまま書く。名前(「解決できないときの縮退」「縮退判定」など)は字面を変えず、指す中身を言い換えて添える
- プロジェクト固有の言葉は、プロジェクトの用語集(既定は `doc/01_overview.md`)に従う
- この表には、ホストの機構名・製品名・モデル名を書かない(役割の名前と一般の言葉で説明する)
- 1 列目の言葉は、2 列目と補足が指す意味で使う所だけに当てる。ふつうの意味や、プロジェクトの言葉として使う所(「型伝播チェーン」のチェーン、CORS の origin など)には当てない
- 2 列目と補足の中に出る表の言葉(決まった語を含む)には、言い換えも説明も添えない(2 列目に置き換えたときも同じ)。その中に出た所は、初めて出す所に数えない

| 周 | 無人ループの 1 回分の実行(タスク 1 件を、新しいセッションで始めから終わりまで回す) | 発見の周は、改善の候補を探す 1 回分 |

## 5. 字面を変えない行と語

skill の手順・references・scripts が書式や照合のパターンを決めている行と語は、字面を変えない。別の工程がその字面で読むので、言い換えると読めなくなる(例: 結果の行の頭に `告。` を付けると、`loop.sh` の照合に一致せず、無人ループの 1 回分が失敗と判定される)。

- **(i) 決まった行・見出し・ヘッダの行・一覧**: 行全体の字面を守る。行頭から字面どおりに書き、同じ行の前後に何も足さない(マーカー・説明・括弧書き・`` ` `` を含む)。説明は別の行に置く。並びが決まっている出力では、決まった位置の外に置く
  - 保留の行の停止条件と、結果の行の理由を番号で示すときは、「番号: 中身」で書く(例: `無人の周の結果: 失敗扱い — G3: 無人の前提を欠く`、`- **保留**(ship-task・YYYY-MM-DD): S4: 承認の後に本文が変わった — 設計レビューをやり直す`)。番号を先に置き、行頭・区切り・結末の値には何も足さない
- **(ii) 決まった語**: (i) の行やフィールドの値として書くときは、字面を守る。文の中では字面を変えずに使い(言い換えない・訳さない)、括弧や続く文で説明を添えてよい

| 状態名の頭 | `進行中_`・`完了_`・`中断_`・`保留_`・`候補_` | `create-task/references/task-directory.md`・`create-task/scripts/resolve-task-dir.py` |
| 要件タグ | `[実]`・`[決]`・`[将]`・`[前]` | `export-doc/SKILL.md`・`init-project/templates/doc/03_requirements.md.template` |
| 指摘 JSON の鍵と値 | 鍵の `verdict`・`issues`・`file`・`line`・`category`・`severity`・`description`・`suggestion` と、値の `APPROVED`・`CHANGES_REQUESTED`・`blocker`・`major`・`minor`・観点の名前 | `do-task/references/review-protocol.md`(`do-task/scripts/review-agent.sh` が `verdict` を照らす) |

## 6. 口調

口調(話し方の型)を当てるのは、人との会話の応答だけ(1 節の表)。わかりやすさの決まり(2 節)は、口調の正本がどれでも常に効く。

**「応答の書き方」節**: 権威参照ファイル(`AGENTS.md`。無ければ `CLAUDE.md`)の、見出しが「応答の書き方」で始まる節。節は、見出しの行から、同じか上の階層の次の見出しの前まで(`#` の数は問わない)。

**口調を決めた別の節**: 「応答の書き方」節のほかで、次の手がかりのどれかに当たり、中身が人との会話の口調(文末・マーカー・話し方)を決めている節。

- 手がかり(どれか 1 つに当たればよい):
  - 見出しに「応答の書き方」「応答スタイル」「話し方」のどれかを含む
  - 見出しに「口調」か「文体」を含み、あわせて「応答」「会話」「返答」のどれかを含む
  - 行頭がマーカー(`^(\| |- )?(是|否|告|解|答|提案|警告|問|依頼|経過|異常)。`)で始まる行を持つ(その行のすぐ上の見出しの節)
- 手がかりに当たっても、中身が会話の口調でなければ当たらない(例: 「API 応答スタイル」「コミットメッセージの文体」)
- 当たる節が入れ子になるときは、外側の節を 1 つの節として扱う
- 探すのは権威参照ファイル。`AGENTS.md` と `CLAUDE.md` が両方あるときは、`CLAUDE.md` の import 行(`AGENTS.md` を import する行)より下の追記も見る(design §3 の読み方)

**口調の正本の決め方**(上から順に見て、最初に決まったものを正本にする):

1. 「応答の書き方」節の中の口調の記述。行頭が `### ` の行から始まる口調の部分か、`###` が無くても決まりの文の外に直に書いた口調の指示(「口調は「…」の節に従う」の行は除く)
2. 「応答の書き方」節の「口調は「<ファイル>」の「<見出し>」の節に従う」の行が指す節。指してよいのは、権威参照ファイル(`AGENTS.md` があるときの `CLAUDE.md` は import 行より下)の中の節だけ。指す先が無いか、その外を指していれば飛ばし、そのことを報告に書く
3. 口調を決めた別の節。2 つ以上あれば、`AGENTS.md` の節を先に、次に `CLAUDE.md` の節。同じファイルの中では先に出る節
4. 1〜3 で決まらないとき(「応答の書き方」節に口調の記述も指す行も無い・指す先が無い場合を含む)は、skill は口調を決めない。ホストが読むほかの指示(利用者の個人の指示・ホスト固有の指示のファイルなど)に口調の決まりがあれば、それに従う。どこにも無ければ、です・ます(マーカーなし)

**報告の型の中の置き方**: skill が決めた報告の型(見出し・表・決まった質問の文)の中では、型と字面を保つ。

- 見出し・表の列名に出る内部の言葉には、その節の本文の最初で言い換えを添える(2 節の 4)
- この型の中では、マーカーを、応答の最初の要約の段落と、問。依頼。異常。警告。に当たる段落にだけ置く。見出し・箇条書きの各項目・表には付けない
- 型の外の応答では、口調の正本の置き方に従う
- 5 節の (i) の行には、マーカーを付けない
- 完了報告のコピー用の枠(8 節)には、会話の口調を当てず、マーカーも付けない。枠の前のまとめと、後の依頼の段落だけに会話の口調を当てる

**食い違うときの順**: 権威参照ファイルの「応答の書き方」節の決まりの文と、このファイルが食い違うときは、skill の中ではこのファイルに従う。

## 7. 質問と選択肢

- 何を決めるのかを 1 文で書く
- 推奨を先頭に置き、「(推奨)」と書く。ホストの質問の仕組みに英語の慣例があっても、人が読む文なので日本語にする
- 各選択肢に「選ぶと何が起きるか」を 1 行で添える
- 選択肢に番号だけを書かない。番号を使うときは「番号: 中身」で、選ぶ内容を一言添える
- 専門用語を避ける(使うときは 4 節の言い方を添える)
- 「質問で確認する」「質問で確かめる」「複数選択の質問」「選択肢つきの質問」など、「質問」で聞くと書いた場面(選択肢を出して答えてもらう問い)では、ホストの質問の仕組み(選択肢を出して答えてもらう道具)を使う。ホストの道具への対応づけは解決表([delegation-map.md](delegation-map.md) §8)
- 1 回に出せる問いと選択肢の数は、実行時にその仕組みの定義で確かめる(数を本文に書かない。出典は design §7-3)。仕組みがあって数を確かめられないときは、1 回に 1 問ずつ聞く
- 質問の仕組みが無いホストでは、同じ内容を文で聞き、答えを待つ。1 回の質問で聞くと決めた問いは、文でも 1 回にまとめる(問いごとに短い文か箇条書きにする)。複数選択の問いは「当てはまるものをすべて」と聞く。前の答えで次の問いが変わるときは、1 つずつ聞く
- 聞き方の形(選択肢つきの質問で聞くか、自由対話で聞くか)・聞く順・まとめ方と区切り方(質問の仕組みが無いときを含む)・答えの後の処理は、各 skill の決まりが先に当たる。質問を省くと決めた範囲(`--yes`・候補モード・無人モードなど。省く範囲は各 skill が決める)と、答えを受け取れない実行でも、各 skill の決まり(尋ねない・保留・失敗扱い・理由を報告する)が先に当たる

## 8. 完了報告の型

作業を終える報告は、次の順に書く。途中で止まったときと、失敗したときも同じ型を使う。完了にできる条件と、止める条件は各 skill のまま変えない。

1. **まとめの段落**: 結論を先に短く書く。会話の口調(6 節)に従う
2. **コピー用の枠**: 下の 7 項目を、この順でコードフェンスに囲む。前後の説明と分け、そのまま別の AI や人に渡せる文にする。段落の印(「告。」など)は付けない
3. **依頼の段落**: 人にしてほしいことがあるときだけ、枠の後に分けて書く。会話の口調に従う。質問の仕組みを使う場面は 7 節に従う

```text
完了: <完了 / 途中で止まった / 失敗> — <Issue 番号: 内容、またはタスク名>
変えたもの: <ファイル数> 件。<主な変更>
確かめたこと: <検査の成功・失敗・未実施の件数>。<レビューの承認数 / 実施数、モデルの名前と版>
動かした確認: <実際に行った操作と観察結果。しなかったら「未実施」と理由>
残っていること: <人の判断や次の作業。無ければ「なし」>
詳しい記録: <PR 本文・Issue の記録・既存の記録のパスなど。無ければ「なし」>
リンク: <PR・Issue の URL。無ければ「なし」>
```

- 検証だけの報告では、「完了」欄には検証の合否を書く。
- 枠の中は 10 行前後を目安にする。「変えたもの」は 1〜3 行、「確かめたこと」は 1〜2 行にする。無い項目は省かず「なし」と書く。ただし、確認をしなかったときは「未実施」と理由を書く
- 検査とレビューは実際の結果を数字で書く。レビューしていなければ実施 0 件と理由を書く。「確かめたこと」に各レビュアーのモデルの名前と版を含める。各 skill が報告を求めるほかの役割のモデルも同じ欄に含める
- モデルの値は [delegation-map.md](delegation-map.md) の「委託先の短い説明」に従う。内蔵の AI は自己申告の値を使う。自己申告が無いときは、起動時の説明の値に「確認前」を付ける。外部の AI は、実行記録のランナー名・CLI の版・モデル名を書く。起動時の説明と違えば、その違いも書く
- 自己申告・起動時の説明・実行記録のいずれでも名前や版を確かめられない場合は「未確認」と書き、役割名や指定用の別名から推測しない
- 「動かした確認」は、自動の検査と区別する。確認しなかった理由と、各 skill が決める確認の状態を落とさない。「未実施」と書くだけで完了にできることにはしない
- 内部の言葉は 4 節の平易な言い方にする。番号だけでは呼ばず、「番号: 中身」と書く。コードの名前・コマンド・パスと、5 節の決まった語は字面を守る
- 変更ファイルの全一覧・検査やレビューの内訳は、PR 本文や Issue の記録などに残し、「詳しい記録」で場所を示す。未作成の記録や URL は書かない。記録する場所が無ければ、必要な内訳を会話に残し、会話のどの見出しや表(例: 生成物一覧の表)に残したかを示す
- 人が開いて確かめるファイル(設計書・決定録・書き出したファイルなど)は、まとめの段落で、9 節のとおりリンクを添えて示す。枠の中のパスは字面のまま書き、リンクの書き方を足さない。枠の「リンク」には PR・Issue の URL だけを書き、手元のファイルのパスは「詳しい記録」などに書く。枠は別の人や AI へそのまま渡す文なので、枠の中の手元のパスは、リポジトリからの相対で書く。リポジトリの外のファイル(自動メモリ・一時ファイルなど)は枠に書かず、まとめの段落だけに置く
- 失敗の理由・未実施の確認・人に求める判断・再開の条件は、詳しい記録を開かなくても分かるように書く。10 行に収めるために省かない。詳しい操作手順が必要なら、依頼の段落に置く
- **書式が決まった最後の行**(`無人の周の結果: …`・`レビュー判定: …` など)は、枠の外に置く。依頼の段落があっても、その後の報告の最後の行のままにする。字面は変えない。決まった一覧と結果の行が続く出力も、5 節の並びを守る
- **`/ship-task` の中から呼ばれた skill は、コピー用の枠を出さない**。必要な結果・記録の場所・停止理由を呼び出し元へ返し、決まった最後の行は残す。最後に `/ship-task` が枠を 1 つだけ出す。途中で止まったときも同じ
- `/ship-task` の各工程の結果と続行判定の内訳は、Phase 5 の手順 3 に従って PR 作成前に本文へ書き、枠ではその場所を示す。作成後は本文を書き換えない。発見の周と PR を作らなかったときは、既存のタスクの記録か会話に内訳を残す。この型のためだけに新しい記録ファイルは作らない
- 報告そのものが成果物になる skill など、この型に合わせない場合は、各 skill の報告手順に理由を書く。途中の質問や進捗の報告にはこの型を当てない

## 9. ファイルへのリンク

人との会話の応答(1 節の表の「人との会話の応答」。完了報告のまとめと依頼の段落を含む)で、ファイルを示すときは、人が開けるリンクを添える。

- 対象: 書いた・変えたファイル(設計書・記録・自動メモリやプロジェクトのメモリのファイル・文書・設定など)と、変える前に確かめてもらう既存のファイル。報告で示すファイルだけに添える。リンクのために、報告にファイルの一覧を足さない(変更ファイルの全一覧は 8 節のとおり PR 本文などに残す)
- まだ無いファイル(作る前の提案)と、消したファイルには添えない。開けないので、パスだけを書く
- 形: ホストごとの形は解決表([delegation-map.md](delegation-map.md) §9)に従う。表に無いホストと、形が未確認の表示では、パスを `` ` `` で囲んで書く(2 節の決まり 4)
- リンクの文字(人に見える部分)は、パスの字面のまま書く(決まり 4)。「設計書」などの名前に置き換えない。何のファイルかは、リンクの前に書く(例: `設計書: <リンク>`)
- 作業ディレクトリ(プロジェクト)の外のファイルは、表示によっては開けないことがある(解決表 §9)。開けなくてもパスをコピーできるよう、外のファイルでも、リンクの文字はパスの字面のまま書く。使ってよい形は、外のファイルでも解決表 §9 に従う
- 行を示すとき・パスの基準(作業ディレクトリからの相対か、絶対か)も、ホストの形に従う
- 人が読むだけの一覧や表(init-project の生成物一覧など。別の工程が字面で読まないもの)のパスにも添える

**足さない所**:

- **5 節の (i) の行と一覧**(結果の行・判定の行・ヘッダの行・候補モードのパスの一覧など): 字面を変えず、リンクの書き方を足さない。理由: 別の工程が字面で読むので、リンクの書き方が混じると照合に一致しなくなる。リンクを示したいときは、別の段落に置く。並びが決まっている出力では、決まった位置の外に置く
- **完了報告のコピー用の枠**(8 節): パスを字面のまま書く。理由: 枠はコードフェンスの中なので、Markdown のリンクの書き方は、リンクにならずに字のまま残る。そのまま別の AI や人に渡す文でもあるので、書き方の字が邪魔になる。開けるリンクは、枠の前のまとめの段落に置く
- **Issue・PR の本文と作る文書**: この節を当てない。理由: 読む人の手元で、そのパスが開けるとは限らない。文書の中のリンクは、その文書の書き方に従う
- **AI への依頼文と、その返答**: この節を当てない(1 節のとおり、決まった書式を守る)
